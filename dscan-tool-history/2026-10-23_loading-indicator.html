A loading indicator while the page waits on zKillboard or ESI

UIBug fix 2026-10-23 · v2026.10.14.38 → v2026.10.14.39 · From Erik's todo-inbox: "add a thinking or loading visual to display while waiting on the results of an api call. sometimes, switching between hull type or fits on the pilot analyzer tab, cards take time to update and it looks like nothing happened after a click." Erik approved doing this first, then My Ship phase 2.

Why it looked like nothing happened

Clicking a hull button (or the last-kill pivot, or Refresh losses) left the old results on screen, unchanged, until the new losses were fetched and calculated. The only sign of activity was the small grey status line at the top of the panel, often out of view.

A second problem showed up along the way. Nothing stopped a second click while the first run was still going. Two hulls clicked in quick succession could finish in the wrong order and leave the first hull's fits on screen.

What changed (presentation only)

  • A bar appears above the results while a run is waiting:
    • it shows a spinner, what is loading ("Loading Curse losses…") and the current step from the status line ("Pulling fit details from the 3 most recent losses…");
    • it is pinned to the top of the screen if you have scrolled down;
    • it waits 250 ms before showing, so an answer that is already cached doesn't make it flash.
  • The old results dim and can't be clicked until the new ones arrive. The button you clicked spins.
  • One run at a time: while a run is going, the other run buttons (Analyze Pilot, Refresh losses, the hull buttons, the last-kill pivot) ignore clicks. This fixes the race.
  • Fit Analyzer: "Analyze fit" has its own bar.
  • Reduced motion: with reduced motion set in the system, the spinner stays still.
  • Not changed: switching between loss tabs, modes and module states. Those don't wait on the network; module states already had their own busy state.

Verification

  • New tools/page_checks/busy_check.py: 18 checks, 0 failures. zKillboard is served by the script with the answers deliberately held back.
    • The bar stays hidden for the first 250 ms, then shows with the right label and the status line's step.
    • Scrolled 1,500 px down, it is pinned 8 px from the top of the screen.
    • The old results are dimmed and unclickable, and the clicked hull spins.
    • A second hull clicked meanwhile is ignored, so the first one is shown.
    • A cached switch never shows the bar.
    • Refresh losses and the Fit Analyzer work the same way, and reduced motion stops the spinner.
    v.38 has no bar, so the check errors out on it.
  • All other page checks (layout, damage chart, My Ship, missing charges, zKillboard outage, card widths) pass. The regression suite and D-scan parse tests pass, and the update-check chain is all OK.

Lesson for future models

When a click starts work that takes time, show the user it started, near where they are looking. A status line at the top of the panel doesn't count. Also block a second click until the first one finishes: without that, two runs can finish in either order, and the screen can end up showing the answer to the earlier click. Check it with a test that holds the network answer back on purpose. With an instant mock, both bugs go unseen.
