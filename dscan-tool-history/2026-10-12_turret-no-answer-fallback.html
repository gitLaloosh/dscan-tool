Turret "No answer" tiles fall back to the 2nd-weakest damage type

2026-10-12 · index.html · backlog item, the owner 2026-10-12: "extend weakness info for weapon systems with 'No answer' to utilize the next weakest resist type to pick an ammo type (flagging that it cannot take advantage of the primary weakness). that way we're at least giving them something useful."

Change

A turret weapon system's ammo-recommendation tile previously dead-ended with "No answer" whenever TURRET_RECS[weakest][system] was null -- laser can never address Kinetic/Explosive, hybrid can never address EM/Explosive (projectile answers all four types directly and never hits this). New secondWeakestOf() reuses the fit's already-computed per-type weighted resist map (same source weakest/weaknessPct already come from) to find the runner-up damage type. New buildTurretRecs() tries the fit's actual weakest type first (unchanged behavior when it has an answer); when it doesn't, it tries the system's recommendation for the second-weakest type instead, and tags the result fallbackFrom/fallbackTo so the render layer can flag it. Both turretRecTileHtml() (Fit Analyzer's boxed tiles) and turretRecText() (D-Scan card's plain-text line) now render a fallback distinctly from a direct hit -- a thin amber left edge + an explicit "Fallback -- can't hit X, next-best is Y" line, never presented as equal to an unambiguous answer. If the second-weakest type also can't be addressed by that system (e.g. weakest=Kinetic, 2nd=Explosive for laser -- neither is EM), the tile correctly stays "No answer": the fallback is a single-level lookup, not a cascade through all four types, per the backlog item's own scope.

Verification

Logic exercised directly against all 6 weakest/second-weakest damage-type combinations in isolation (bypassing the DOM) -- every fallback-succeeds and fallback-still-fails case matched the TURRET_RECS table's own hand-verified combinations exactly. Also scanned all 79 existing golden fits: the overwhelming majority naturally hit a fallback on at least one system (laser and hybrid's null cases are common, not edge cases), confirming this was a far more frequent dead end than "No answer" suggested.

This field (turretRecs) was never flattened/asserted in the regression suite before this fix (display-only, same situation sensorStrength was in before 2026-10-11). Added a flattening block to run_regression.mjs (turret{Laser,Hybrid,Projectile}Name/...Fallback) and pinned it on 3 real, already-existing fits rather than constructing a new one:

  • curse_zkb139073592_ewar (weakest Thermal) -- laser falls back Thermal→EM to "Radio", hybrid/projectile stay direct hits. The fallback-succeeds case.
  • caracal_zkb136427798 (weakest EM) -- hybrid falls back EM→Thermal to "Iridium or Thorium", laser/projectile stay direct hits. The complementary fallback-succeeds case (the other null-prone system).
  • rifter_user (weakest Thermal, 2nd-weakest neither Thermal nor EM) -- laser stays "No answer" even after the fallback attempt, hybrid/projectile unaffected. The genuinely-still-unaddressable negative control.

Also Playwright-screenshot-verified all three cases rendered through the real renderFitSummaryHtml() against the real extracted CSS -- fallback tiles show the amber edge + caveat text, direct-hit tiles are pixel-identical to before, and the still-"No answer" tile is unchanged.

Full suite: 79/79 fits, ALL PASS. dscan_parse_tests.mjs: 280/280 PASS.
