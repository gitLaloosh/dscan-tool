Pilot Analyzer: a plain message when zKillboard's API is down

BugExternal 2026-10-23 · v2026.10.14.30 → v2026.10.14.31 · Erik: "the pilot analyzer is failing on the published site. wont load zkillboard info." Then "ok go with option 1" (a clear message, no automatic retry).

Cause: zKillboard, not the tool

  • Tested from Erik's computer (the built-in browser), 2026-10-23 around 01:30 UTC. The zKillboard site itself loaded and showed new kills. Every API request (/api/losses/characterID/…, /api/kills/characterID/…, /api/losses/shipTypeID/587/) hung for 40–60 s, then answered {"error":"API result unavailable, please try again later"}.
  • zKillboard's source (view/api.php, cron/9.queueAPI.php):
    • Since 2026-09-11, every API request is queued for a background worker. The request waits up to 60 s for that worker's result.
    • Commit ffc94263, "Remove race condition for api queue" (2026-10-22 17:48 US Eastern), made a request with no result after 60 s answer 503 with that message.
    • So the queue is not producing results. No open issue on their GitHub at the time.
  • On the page this looked like "Checking…" for a minute, then "server error (status 503). Check your network connection to zkillboard.com and esi.evetech.net", which blamed the user's network.

What changed

  • New zkbFetch(url), used by both zKillboard calls (the last-kill lookup and the losses lookup). It gives up after ZKB_TIMEOUT_MS (20 s). On a timeout or a 5xx it throws one plain message: "zKillboard's API isn't answering right now. That's on zKillboard's side, not your connection. Try again in a few minutes". The error is marked zkbUnavailable.
  • After a failure, zKillboard calls in the next 60 s (ZKB_COOLDOWN_MS) fail at once. The two lookups run one after the other, so the page answers in about 20 s instead of 40.
  • The Pilot Analyzer's status line no longer adds "check your network connection" to this message.
  • Nothing is cached on failure; a later try asks zKillboard again. There is no automatic retry, per Erik's option 1.

Verification

  • New tools/page_checks/zkb_outage_check.py runs the real page with zKillboard served three ways: 503, no answer at all, and an empty list. All three pass (FAILURES 0): outage message in the status line and the last-kill box, no network hint, gave up in 0.1 s and 20.1 s, normal texts when zKillboard answers. v.30 fails.
  • No number changes. Suite ALL PASS; full output diff v.30 → v.31: 0 of 237 fits. PYFA CORE lock unchanged; parse tests 293/293; layout check FAILURES 0.

Lesson for future models

  • When a third-party API fails, reproduce it from a real browser on the user's machine, then read the provider's own source and recent commits before changing anything. Here the provider's commit from the night before explained the failure exactly, and the fix on our side was only to fail fast and say so plainly.
