Keeping up with EVE patches: fresh item data, a patch-day report, and a note on changed items

Data 2026-11-04 · v2026.11.04.3

Why

  • Build queue 008, Project doc roadmap/game-data-update-plan.md. The owner (2026-11-02): "Eve has an expansion releasing on Nov 10th. Can you find out what the update process generally looks like for tools like ours? How do we identify stat changes, new skills or modules, etc. Also need to address any implication on pyfa calculations changing."
  • A mockup came first (Claude outputs/game_data_note_mockup.html). His answers: the place and amber "this is fine"; "keep the rule" (the short line, the rest on hover); the Fleet tag "on the hull is fine"; "status line is good but make it "Item data refreshing" if that's what it's actually doing". The workflow file: "You paste it in". Order: "008 first".
  • Not brought back: the amber note after every EVE build (gone since v2026.10.29.4). The note now shows only on items that changed.

What changed

  • Item data after a patch (section 1):
    • Once per page load the page asks ESI for EVE's server version (/status/). When it differs from the last one seen, the item data kept in the browser (types and groups, a week) is dropped before the first lookup, and "Item data refreshing" shows where the version tag is, for a few seconds.
    • The first lookup waits for this at most 3 s. A slow or failed answer: the kept data is used as before, and the next load asks again.
    • The first visit only remembers the version. Killmails, zKillboard answers and organisations are never cleared by it. No cache-busting.
  • A note on changed items (section 3): GAME_DATA_PENDING, the items changed in EVE's update and not yet checked against pyfa (empty today).
    • A fit that uses one, in the Fit Analyzer, a Pilot Analyzer loss or My Fit: "Changed in EVE's update:" and up to 3 names, then "+N more", above the cards. The hover gives the build, every name, and "This tool checks its numbers against pyfa after pyfa updates; until then they may be off."
    • The Fleet tab: a small amber "changed" tag after the hull's name. Ships on scan: the line in that hull's card.
    • The cargo doesn't count. Never on Intel, never page-wide.
  • The patch-day report (section 2), tools/sde_change_report.py: what changed in CCP's data since the build pyfa's data came from. New items, published or not, attributes old → new, effects added or removed, and for each new effect whether pyfa has a handler. With --write it updates the page's list. It reads only the five files it needs from CCP's zips (about 25 MB a build).
  • The pyfa update empties the list (PYFA_CORE.md step 5).

For the owner: the workflow job to paste

The build can't write .github/workflows/jump-table.yml. Paste this at the end of that file, under jobs: after the check job (same indentation as check:). It runs on the same schedule. It opens a pull request only when the list of changed items changes; it never commits to the main branch. Its steps were run here against made-up copies of CCP's site, but the job itself only runs on GitHub: the first real run shows in the Actions tab.

  # v2026.11.04.3 (build queue 008, tools/sde_change_report.py): after a CCP build that changed ships, modules, charges,
  # skills, drones, implants, subsystems or fighters since the build the page was checked against pyfa, open a pull request
  # with the report and the page's updated list of changed items (GAME_DATA_PENDING). Never commits to the main branch.
  game-data:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v4
      - name: pyfa's newest release (only its effect handlers, for the report)
        env:
          GH_TOKEN: ${{ github.token }}
        run: |
          tag=$(gh release view -R pyfa-org/Pyfa --json tagName -q .tagName)
          mkdir -p "$RUNNER_TEMP/pyfa/eos"
          curl -sSfL "https://raw.githubusercontent.com/pyfa-org/Pyfa/$tag/eos/effects.py" -o "$RUNNER_TEMP/pyfa/eos/effects.py"
          echo "version: $tag" > "$RUNNER_TEMP/pyfa/version.yml"
      - name: Compare CCP's newest item data with the build the page was checked against
        id: report
        run: python3 -I tools/sde_change_report.py index.html --pyfa "$RUNNER_TEMP/pyfa" --write --body "$RUNNER_TEMP/game-data-pr.md"
      - name: Open a pull request (only when the list of changed items changed)
        if: steps.report.outputs.changed == 'true'
        env:
          GH_TOKEN: ${{ github.token }}
          BUILD: ${{ steps.report.outputs.build }}
          BASE: ${{ github.event.repository.default_branch }}
        run: |
          branch="game-data/build-$BUILD"
          if git ls-remote --exit-code --heads origin "$branch" > /dev/null; then
            echo "A pull request branch for build $BUILD already exists ($branch); nothing to do."
            exit 0
          fi
          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git checkout -b "$branch"
          git add index.html
          git commit -m "Game data: items changed in EVE build $BUILD"
          git push origin "$branch"
          gh pr create --base "$BASE" --head "$branch" --title "Game data: items changed in EVE build $BUILD" --body-file "$RUNNER_TEMP/game-data-pr.md"

Choices made while building

  • No shared /status/ call: the plan said to share Intel's call, but the page hasn't made one since v2026.10.29.5. It's now one call per load, started as the page loads.
  • The "changes" fallback gives IDs, not values: CCP's changes/<build>.jsonl files only say which items changed (LESSON #133). When the older zip is no longer published, the report lists those items as "changed (old values not published)".
  • pyfa's data build isn't an SDE build: 3624425 isn't published. The report compares from the newest SDE build at or before it (3607705 today), found through the changes files.
  • Its own job: the report is a separate job, so its pull request and the jump table's never share a branch.

Checks and gates

  • New tools/page_checks/game_data_check.py (see tools/README): the version check with a stand-in /status/ on six loads, and the note on a copy of the page with a made-up list, in every place it shows and none it doesn't. The old page fails it.
  • New tools/independent_checks/check_sde_change_report.py: the report on made-up CCP data, a local server standing in for CCP's site (with and without range requests, the older zip gone, nothing changed). In the chain.
  • New tools/check_game_data_pending.py: the list in the tools' form. A fast lint and a chain step.
  • check_request_gates.py lists the new ESI call (gdServerVersion).
  • 26 mutants, all caught: 17 on the page (clearing other stores, clearing on the first visit or the same version, waiting forever, not waiting, a late answer clearing, a /status/ per lookup, saying nothing, the note on every fit, the cargo counted, 4 names, the Fleet tag or scan line on every hull, the line below the cards, a pressable tag, a note page-wide, the plan's full sentence) and 9 in the report and list check. One was missed at first (the first lookup not waiting): /status/ is now held back inside the page, so the wait is measured.
  • The whole run (run_checks.py --auto, every tier): 13 lints, the pyfa chain and 69 page checks in 37 min. It caught two older checks that counted every request (alert_sound_check, intel_check): the page now asks /status/ once as it loads. Both now leave that one out (Intel itself still asks nothing) and pass. extension_check was flaky under load and passed alone.
  • Page size: 735,221 → 737,330 bytes gzipped (+2.1 KB), under the 800 KB stop. No perf harness: Intel's drawing isn't touched.

Lesson for future models

LESSON #133: a data source's name says what it's about, not what's in it. Open one real file before a plan counts on it, and write its fields into the plan. CCP's "changes" files hold IDs, not values.
