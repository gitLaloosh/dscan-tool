Capacitor Booster: cargo-inference fallback + bounded range for the no-data case

2026-10-12 · dscan-tool.html · direct follow-up to the Capacitor Booster gain-modeling feature shipped earlier the same day

Erik asked: "if the fit has a module that uses boosters but doesn't have charges loaded, account for the possibility and provide boosted/unboosted numbers anyway. any issue with this?" The honest issue: Capacitor Booster charges span a genuine 25–3200 GJ range (~128x) with no hard compatibility gate on the module side (confirmed live: neither the Medium F-RX Compact nor the Small Capacitor Booster II's own dogma attributes include a chargeSize gate), so inventing a single number for a module with zero charge data anywhere would be a guess, not a calculation. Two concrete, fully grounded options were offered instead, and Erik approved both: infer from spare charges sitting in cargo when they exist, and show a real bounded range (not a single invented figure) when nothing at all is available.

1. Cargo-inference fallback

A Capacitor Booster module with no charge sharing its own Mid-slot flag (nothing was loaded at time of death/paste, or the charge sits unracked) very often still has its real charge type sitting as spare reload stock in Cargo/Fleet hangar — the real Curse killmail is a direct example: 4 spare Navy Cap Booster 800s sit in Cargo alongside the one that happened to be loaded. This reuses the exact same cargo-scan shape as the existing turret/launcher cargo-ammo-fallback (same cargoIds, same analyzeChunks pattern), matched by ESI group name (Capacitor Booster Charge, group 87) rather than a hardcoded id list. When multiple distinct charge types sit in cargo at once, the one with the most copies on hand wins (tie-broken by largest GJ) as the most likely real reload stock.

The resulting figure is numerically identical to a confirmed-loaded charge of the same type — it's the same real GJ/cycle time math — but the card is honest about the difference: a new fromCargo flag swaps the wording from "a loaded X actively cycling" to "a spare X actively cycling (inferred from spare charges in cargo, not confirmed loaded)".

2. Bounded range for the true no-data case

When no charge can be found anywhere (neither flag-paired nor in cargo), rather than guessing or staying silent, the card now shows a genuinely grounded envelope: every real Capacitor Booster Charge type that exists (all 18 confirmed live this session via ref-data.everef.net/groups/87 — 9 GJ tiers × plain/Navy variants, no others exist) is filtered down to only the ones whose own volume actually fits inside this specific module's charge-bay capacity (attribute 38) — the one real physical constraint that exists, since there's no chargeSize gate to narrow it further. The smallest and largest charges that pass that filter bound the range, each run through the full stability simulation (not just a raw GJ/s figure), so the card reads the same way as the confirmed-boosted case: "if loaded, gain could range 2.1–33.3 GJ/s depending on charge size (smallest fitting charge: stable at 72.1%; largest fitting charge: stable at 100%)".

A 3rd pre-existing fixture gap, found the same way as the first two

Testing the new range fallback against the Ishkur golden fit's own real fitted Small Capacitor Booster II (which genuinely has no charge data at all) surfaced that this type's cached dogma stub was missing attribute 73 (cycle duration) entirely — the same class of data-completeness gap found twice earlier this same day (the Nosferatu's missing attribute 90, the Ishkur hull's missing attribute 55). Fixed with the live-confirmed value (12,000ms, ref-data.everef.net/types/3568).
