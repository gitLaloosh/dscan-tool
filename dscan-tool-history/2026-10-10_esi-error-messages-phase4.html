Richer ESI/zKillboard error messages + visible failure warnings — Remediation Plan Phase 4

Date: 2026-10-10   Status: Delivered, 28/28 regression PASS, byte-identical before/after diff, verified in real Chromium

What this fixes

ARCH-4 (logged 2026-10-09): ESI fetch failures threw bare, context-free messages — the canonical example was getType()'s throw new Error('type fetch failed'), which carries no type id and gives no way to tell "ESI doesn't recognize this id" (404) apart from "we're being rate-limited" (420/429, recoverable by waiting), "ESI itself is down" (5xx), or an actual network failure (no response at all). All four looked identical from the UI. Separately, a per-type lookup failure during a D-Scan analysis was silently dropped from the Contacts grid with zero indication anything had gone wrong — a contact that failed to resolve just vanished, indistinguishable from "this scan had fewer contacts."

The fix

  • New helper describeEsiFailure(context, status, detail) builds one consistent, readable message for every ESI/zKillboard fetch site: distinguishes network failure, 404, 420/429 rate-limit (with a "wait and retry" hint), 5xx server error, and any other rejected status — always including the failing id/context and, where available, the response body.
  • Applied it to every ESI/zKillboard fetch site that previously hand-rolled a thin message: getType(), getGroup(), resolveNamesToIds(), resolveIdsToNames(), fetchLossesStubs(), fetchKillmail(), and the zKillboard fetch inside renderLastKill().
  • analyzeChunks()'s per-item catch now keeps the original item ({error, item}) alongside the error message, instead of discarding which lookup actually failed — purely additive, every existing caller already only reads .error and ignores unknown fields.
  • runAnalysis() now collects any per-type lookup failures and appends a visible, non-blocking warning to the scan's status line (e.g. "⚠ 1 type(s) couldn't be fetched and are left out below: BrokenShip (Type 999999 fetch: not found (status 404))") instead of letting them disappear silently. The scan still completes and shows everything that resolved — this only makes the gap visible.

This is purely a change to error messages and to what's shown on failure — it never changes when something throws vs. succeeds, so it cannot touch any DPS/EHP math.

Files/functions changed

  • New: describeEsiFailure(), declared near the ESI/ZKB constants.
  • getType(), getGroup(), resolveNamesToIds(), resolveIdsToNames(), fetchLossesStubs(), fetchKillmail(), renderLastKill() — each fetch site now wraps the network call in try/catch and routes its failure message through describeEsiFailure().
  • analyzeChunks() — per-item catch now also stores the original item.
  • runAnalysis() — status line now appends a visible warning for any per-type lookups that failed, instead of letting renderResults()'s existing continue-on-error silently drop them with no trace.

Deliberately NOT touched

getWeaponDamageInfo()'s own internal try/catch (falls back to {mode:'unknown', types:[]} on any getType/getGroup failure) and fetchKillmail()'s already-graceful "no hash" short-circuit were left as deliberate, reasonable degradations for cosmetic weapon-badge/last-kill display — not the thin-error-message pattern ARCH-4 was about. fetchKillmail()'s own error message was still upgraded to use describeEsiFailure() for consistency, but its graceful-return-instead-of-throw contract is unchanged.
