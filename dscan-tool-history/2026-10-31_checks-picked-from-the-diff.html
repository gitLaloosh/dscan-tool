Checks picked from what changed

ProcessChecks 2026-10-31 · page unchanged (v2026.10.31.7)

Why

A review of the tiered check routine recommended choosing the level from the changed files instead of by hand, counting the calculation chain's inputs as calculation changes, short timeouts per check, and a time-limited quarantine for flaky checks. Our response agreed and named the next steps: a picker that reads the changed lines and includes the calculation inputs, per-check timeouts, and quarantine with an expiry. The owner asked whether they were built; they weren't, apart from the timeouts (15 minutes each). He said "yes please" to building them.

What changed

  • New tools/check_picker.py, used by run_checks.py --auto.
    • Nearly every change lands in index.html, so it maps the file's changed lines, not the file. A line inside a PYFA CORE section or the engine goes to the calculation tier. A line in one area's function (its name's prefix: it Intel, sa System Analyzer, pd the dossier, and so on) goes to that area. Otherwise the line takes the area of the section it sits in. Shared code means everything.
    • CSS goes by class name, and an unowned class means every page check, but not the 40-minute chain (CSS can't change a number). Changes to the card and info text and the error codes go by their key. Comments, blank lines and the version tag count for nothing.
    • Other files: the calculation's inputs (the golden fits and fixtures, the table generators, the independent checks, the pyfa tools and manifest) mean the calculation tier. A page check means its areas and those of the checks built on it. Docs and lints mean the fast lints only. Anything not listed means everything. Every 5th delivery means everything.
    • The changes come from git when there's a .git folder, or from --since a copy of the repo as last delivered. --plan only says what it would run.
    • Tried on the last 14 deliveries (the saved copies of each). Where the ledger has a hand pick, the picker named every area the hand pick did, except "layout" three times, where the CSS that changed was one area's own. It often named more: the full set four times (shared code or the tab bar changed) and the calculation tier twice (a calculation input or a slider helper inside the weakness picks' section).
  • The fast lints gained the regression suite and the D-Scan parse tests. They take about 8 seconds and load the page script the way the chain does, so a start-up error is caught on every delivery, not only on calculation runs. The picker's own --self-test is a lint too: 11 made-up one-line edits of the real page, each with the areas it must map to, and every section start found once. 5 mutants of the picker were all caught.
  • Timeouts: 5 minutes per page check (was 15). intel_kills_check gets 10, as its longest run under load was 333 s.
  • Quarantine: a table in tools/check_ledger.md (check, why, since, until). A quarantined check still runs, but its failure doesn't fail the run until the date. After the date it fails the run again. A row needs a reason and lasts 14 days at most (--check-tags fails otherwise). The table is empty: the flaky check was fixed instead.
  • intel_guard_check fixed. It took the read-back's pace from the page's fetch() calls, which run a moment after the gate gives each request its start. On a busy machine the first call ran late, and the average came out 5.09–5.10 a second against a limit of 5.05. It flaked at v2026.10.31.1 and .7 and passed alone both times. It now times the gate's own starts (at least 200 ms apart, 5 a second on average) and still checks that the fetch() calls are at most 6 in any one second. It passed with 8 busy processes on the 2-core machine.
  • A lint that PYFA_SRC is the verified pyfa. The first full run of this delivery failed one chain step, the Intel ship-name table, because the machine had two pyfa checkouts and the checks had been pointed at the older one (v2.69.2) found first by a file search, not the verified v2.69.3. Everything else passed on the old data. run_checks.py --check-pyfa-src now compares the checkout's commit with tools/pyfa_core_manifest.json on every run, and the runner shows the chain's "what moved" lines (LESSON #116). The full run was repeated on the verified pyfa.
  • --jobs defaults to twice the cores, at most 6: the check machine has 2 cores, and 6 browsers at once is what made the timing flakes.

The ledger review (10 rows, v2026.10.30.2 to v2026.10.31.7)

  • What caught real problems: each feature's new check and its mutants, every time; the fast lints (personal data once, card names twice, request gates once, the Intel info text's word limit once); two unchanged page checks outside the change's own (intel_kills_check at v2026.10.30.3, system_analyzer_check at v2026.10.30.4); and looking at the page: the previews, the mockups and the owner's screenshot (v2026.10.31.7, LESSON #114).
  • The pyfa chain ran twice (the two full runs) and caught nothing, because no calculation code changed in these ten deliveries. It stays: it's the only guard for calculation changes, and the picker now runs it only when they happen.
  • No slow check moves to the full tier only: the area tier already keeps unrelated checks out.
  • Flakes: six in ten runs, all timing under load on 2 cores (busy_check, request_gates_check, extension_check once each; intel_guard_check twice; intel_kills_check once, with mutants running beside it). The fixes are the two above.

Checks

  • run_checks.py --auto --since the delivered v2026.10.31.7 picked the full tier (every 5th delivery). On the verified pyfa: 12 lints, the pyfa chain (20 minutes, every step passed) and all 55 page checks passed in 32 minutes, with no flaky check (4 at a time). The longest page check was intel_kills_check at 345 s; the rest finished within 133 s.
  • check_picker.py --self-test: 5 mutants (the Intel prefix sent to the System Analyzer, the Intel CSS unowned, the chain dropped, a section renamed, comments counted), all caught.
  • intel_guard_check: passes alone and under 8 busy processes on 2 cores. A gate 5% too fast is caught by the page's own tripwire in the start the Intel checks share.
  • The quarantine: a quarantined failure is reported and not counted, an expired one fails the run, and a row over 14 days, without a reason or naming no page check fails --check-tags (simulated).

Lesson for future models

LESSON #115: time what the code promises where it makes the promise. The guard check read the clock one step later than the gate it tested, and a busy machine moved that step. When a check flakes only under load, look for that before raising a tolerance.
