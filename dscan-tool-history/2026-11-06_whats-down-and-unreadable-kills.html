What's down, and one unreadable kill file

Page 2026-11-06 · v2026.11.06.6

Why

  • Build queue 015, Project doc roadmap/outage-notices-plan.md, mockup Claude outputs/outage_notices_mockup.html (approved 2026-11-05 and 2026-11-06). The owner, 2026-11-05: "we need to be able to identify this and let users know when it happens so they're not just looking at an empty feed." 016 built the strip and its first line (zKillboard's kill feed can't be read); this adds the rest.
  • Build queue 019, Project doc roadmap/r2z2-unreadable-kill-plan.md: after zKillboard fixed its doubled CORS header (2026-11-06), kill files published before the fix stayed unreadable, and Intel's read-back kept asking for one of them every 30 s, so live kills never came. The owner left it to the build session whether to deliver it with 015: it is here because both change the kill reader and what the strip says about it.

What changed

  • ESI down: a lookup that comes back with nothing the browser may read (ESI's maintenance answer carries no CORS header) or 502, 503 or 504, while the browser is online, makes one /status/ call. If that fails too, the strip says "EVE's ESI is down (maintenance). Names, fits and new kills won't load until it's back. Checking every minute.", the gauge says "ESI down", Intel's Feed note and status line say why no kills come, and /status/ is asked once a minute until it answers (one timer, only while down). Lookup errors that failed for this say "(ESI is down)". While ESI is down, the unreadable-feed line gives way to it.
  • EVE's daily downtime: from 4 minutes before 11:00 UTC the strip counts down to it; at 11:00 one /status/ asks whether ESI is down, and if so the line says it's the daily downtime. Nothing is shown when ESI is fine.
  • zKillboard's pause: its line uses ZKB-01's own words (the owner's choice), counting down, gone when the pause ends.
  • The feed behind: from the kills the reader already read (nothing extra asked), fewer than 40 in the last 15 minutes by zKillboard's publish time (the owner: "40 per 15 min"), or a median age over 30 minutes, once the reader has caught up: the strip, "Kills slow" in the gauge and a Feed note. It goes after 5 minutes back to normal. The line says "in the last 15 min" (the mockup's example said 30) so the number matches the rule.
  • One unreadable kill file: a read-back keeps every readable kill. The unreadable ones are asked once more, together, 6 s later. Still unreadable, published (at or below sequence.json's number, or a later one read) and with sequence.json readable when read again then, they are read past as gaps; from then on an unreadable file doesn't hold the rest of a batch back. A kill not published yet stays "not there yet" (the owner: "Published only"). If sequence.json can't be read either, the feed is down, as before. Three passes in a row with every kill file unreadable count as the feed being down (016's notice).
  • Nothing is kept in the browser that wasn't before.

Checks

  • New outage_check.py (Intel's own start from intel_check.py, on a copy of the page with shorter waits; R2Z2 and ESI as stand-ins, never the live services), all of the plans' cases: one unreadable file asked exactly twice and read past, the rest read once; 40 in a row read past within a few passes; unreadable once, then fine; the whole feed unreadable; every kill file unreadable with the index fine; zKillboard's 429 during a read-back; ESI down (one /status/ to confirm, once a minute while down, all gone when back); one failed lookup while /status/ answers; ESI down over the unreadable feed; two lines at once; the downtime at 10:56 and 11:02 UTC; the pause's countdown (the line written once); the feed behind, and a stale sequence.json that isn't.
  • Mutants: each caught: no retry (read past on the first failure), retried without end, the readable ones after a failure thrown away, read-past kills counted toward the notice, held-back kills read past, kills not yet published read past, read past without reading sequence.json now (caught by intel_guard_check), the strip on one failed ESI lookup, /status/ twice a second, the ESI line left up after recovery, the unreadable-feed line shown instead of ESI down, "behind" never shown, "behind" from a stale sequence.json.
  • Building it: the plan's retry could never have run, since a failed read in a read-back held the rest of its batch back (they came back "not sent"); now the batch goes on once a gap has been read past, and the retry is sent. And the plan's "sequence.json read in the last minute" would have read a feed that had just died past as gaps (up to 300 requests in that minute); sequence.json is now read once when the retry fails, one request a batch.
  • Changed for the new behaviour: intel_check.py's R2Z2 stand-in (above), intel_guard_check.py (after a failed read in a read-back, that one is asked once more, then sequence.json), feed_down_check.py (the same pass reads sequence.json), check_request_gates.py (esiDownCheck listed; its one-a-minute timer checked).
  • The full tier (run_checks.py --auto picked all): 13 lints, the pyfa chain and 73 page checks in 37 min. It caught one thing: the Intel checks' shared R2Z2 stand-in failed every kill file unreadably as a shortcut for "no kills", which 019 now rightly treats as the feed's kills being unreadable (the notice came on in intel_redraw_check). The stand-in now answers a readable 404 for a kill that isn't there, and the 12 checks built on it pass. Regression suite ALL PASS; check_pii 0 problems.
  • Page size: 756,781 → 760,082 (+3.3 KB) bytes gzipped (gzip -9), under the 800 KB ceiling.

Lesson for future models

  • LESSON #142: in a sync Playwright check the stand-ins answer only while Playwright runs, so never time.sleep; restart a reader the way the page does (a new generation), not by swapping its state; wait for what the user would see.
  • LESSON #140 again: one bad item (a kill file) shouldn't stall the rest; read past it once you know the source itself is fine.
