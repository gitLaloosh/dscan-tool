The jump table kept current, no warning

ChangeToolsTests 2026-10-29 · v2026.10.29.4 → v2026.10.29.5

The owner asked what the amber line "EVE is on build 3660036; the jump table was checked on 3654997: a gate EVE added since may be missing" meant, then: "Eve deploys patches very often. is there a way to automate the update so the user never has to see it?" He chose a pull request for each real change.

How it was checked

  • CCP publishes the game's static data with each build. tranquility/latest.jsonl named build 3660036, released 11:10 UTC, ten minutes after downtime; the server was on the same build.
  • Read in the owner's browser pane (only the 0.5 MB stargate file out of the 99 MB download): 13,978 gates, making 6,989 connections, exactly the page's table from the client's file (build 3654997). None missing either way. The warning was a false alarm, as it would be after nearly every patch.

What you get

  • No amber warning, and no request to ESI's /status/ when Intel starts. The info panel says the table comes from EVE's published stargate data and is checked against each new build every day.
  • .github/workflows/jump-table.yml runs at 11:47 and 23:17 UTC (and from the Actions tab). It runs tools/jump_table_update.py: when the gate connections differ from the page's table, it opens a pull request with the new table, naming each connection added or removed. Otherwise nothing happens. It never commits to the main branch.
  • tools/gen_intel_tables.py (the client's own file) compares connections only, so a newer client with the same gates matches.
  • The owner turned on, once, Settings > Actions > General: read and write permissions, and Actions may create pull requests. After merging one: git pull before the next commit.
  • No number the engine works out changed. Jump counts are unchanged.

Checks

  • independent_checks/check_jump_table_update.py (a new chain step): the updater on made-up copies of CCP's file layout built from the page's table. The same gates on a newer build change nothing. One connection removed and one added (to a new system): changed, the build, a pull request naming both, the table rewritten with exactly the new connections, nothing else in the page changed; --check exits 1, then 0. A broken updater (no "changed" output) is caught.
  • A second new chain step runs the real comparison; from the cloud workspace CCP's site can't be reached, so it says "skipped" there and the Action does it.
  • intel_check.py: EVE on a newer build than the table: no warning, no /status/ request, the info panel's new line. v2026.10.29.4 fails.
  • Regression suite ALL PASS (269 fits). Update-check chain: 47 steps, all OK. All 45 page checks pass (extension_check.py failed once in the parallel run, under load, and passes on its own, as before). The lints, the personal-data check and the request-gate check (now 12 fetch calls) report 0 problems.

Lesson for future models

LESSON #100: a warning that fires on a routine event teaches people to ignore it. Compare what matters (the gates), not a proxy that changes for other reasons (the build). When the check needs data the page can't cheaply get, run it on a schedule where the data is, and hand the owner a pull request only when something really changed.
