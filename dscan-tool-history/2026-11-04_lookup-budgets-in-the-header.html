Lookup budgets in the header, and the zKillboard pause counted down

Why

  • Build queue 012, Project doc roadmap/budget-gauge-plan.md. The owner (2026-11-03): "add info to the page that lets the user see what their ESI and zKill budgets are. update the number as it changes. i have been running into zkill not responding frequently but i've also been loading larger datasets. it would be helpful (for now) to have these numbers visible at all times so i know how quickly (and which actions) my budget's being used. make sense? high priority".
  • On the pause: "please show me how long the pause is and count it down for me", and "this is dangerous for the user because they might mistakenly extend the wait time by constantly retrying the search if not given a warning about doing so". A mockup came first; he picked option A (Analyze stays pressable).
  • The build session's review against the latest main (2026-11-04), answered by the owner: ESI is counted by kind of lookup, not by feature ("let's go with your recommendation"); amber from 80 of 100 and "used by" kept across reloads. The header check was run in his browser on the live page: ESI's rate-limit and error-limit headers are both readable there, so the page shows ESI's own numbers.

What changed

  • The gauge, beside the version tag: zKill 37/100 · ESI ok · Kills ok.
    • zKillboard: lookups in the last 10 minutes of the page's 100; amber from 80; "zKill full m:ss" at 100; "zKill paused m:ss" while zKillboard isn't answering.
    • ESI: "ok"; amber "ESI N errors" from 50 errors in a minute, or "ESI low" when a route group is under 20% of its allowance; "ESI wait m:ss" after a 420 or 429 (Retry-After, else the error limit's reset, else 60 s).
    • Kills (only while Intel is on): "ok", or "Kills stopped m:ss" during the hour's stop.
    • Amber when near, full, paused or stopped, never the Hostile red. On a phone it is its own 44 px row above the name; below 480 px "zKill" is "zK" and Kills its dot and time, below 380 px the state words go too (the worst case, all three stopped at once, measured at each width).
  • The panel (press the gauge): zKillboard's count, a bar, when the next one frees up, who used it (System Analyzer, Pilot Analyzer, Fleet tab, Kill link), and the pause note (the time left, failures in a row, "Pressing Analyze now sends nothing and doesn't add time", the next wait). ESI: errors this minute (ESI's own count when its answers carry it), the route group's allowance, the last 15 minutes by kind of lookup (item data, names, killmails, corporations and alliances, pilots, systems and gates, server status). Intel's live kills: the rate, or the stop. The shared close button; Escape and a press outside close it.
  • ZKB-01 says the time and counts down wherever it shows (the status lines, the Last Kill line, the System Analyzer's notes, the Fleet rows): "zKillboard's API isn't answering, so the page waits m:ss before asking again. Pressing Analyze now sends nothing and doesn't add time; if it still doesn't answer after that, the next wait is M min". At 0: "zKillboard can be asked again". Pressing during the pause sent nothing before too; now the page says so.
  • One way to ESI: every ESI request goes through esiFetch, which sends it exactly as before and only reads the answer's headers. Nothing new is asked of ESI or zKillboard.
  • Kept in this browser, shared by its tabs: dscanZkbWho (who used zKillboard) beside dscanZkbBudget, whose list of times is unchanged; dscanEsiUse, ESI's counts per minute per kind, saved at most once a second and when the page closes.
  • Timers: none while nothing counts down. One 1 s tick runs only while a countdown shows or the panel is open, never in a hidden tab (the Retry buttons' countdown moved onto it, so it now pauses in a hidden tab too and is right again on return). The zKillboard count goes down on one timeout set for when the oldest lookup ages out.

Stored data, both ways

  • Upgrading: a browser with only the old dscanZkbBudget list shows its spends as "Other" until new ones come in.
  • Reverting: the older page reads dscanZkbBudget exactly as before and ignores the two new keys.

Lesson for future models

  • LESSON #134: a plan's promises about the code are guesses until checked against it. "Pass who from the call site" assumed the call site knows who is asking (ESI's are in helpers with 30 to 50 callers each); "refresh on the existing timer" assumed it always runs (only with Intel on); "the message counts down" assumed the text is built where it is shown (it is fixed when thrown and shown in about 16 places).
  • LESSON #135: saving a growing list to localStorage on every event rewrites the whole list each time. Keep a small fixed shape (counts per minute) and save on a timer.
  • LESSON #136: a replace checked for one match before an edit can match twice after it. Moving the status line, its text was also inside the moved copy, and both were removed; count where the replace runs.
  • CLAUDE.md step 5's stored-data rule was the wrong way round ("still reads the old format, so reverting stays safe"): reading the old format makes upgrading safe; reverting is safe only when the older page can read what the new one writes. It now asks for both.
