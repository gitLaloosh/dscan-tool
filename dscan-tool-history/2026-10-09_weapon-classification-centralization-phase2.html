Weapon-classification centralization (ARCH-2 fix) — Remediation Plan Phase 2

Date: 2026-10-09   Status: Delivered, 28/28 regression PASS, byte-identical before/after diff

What this fixes

ARCH-2 (logged 2026-10-09 in the architecture critique): classifyHighSlotItem() and getWeaponDamageInfo() each carried their own private copy of the exact same "is this group name a turret/launcher-type weapon" check — a literal duplicated regex, /turret|launcher|weapon/.test(g) || g.includes('vorton projector'). This is the precise bug class the EDENCOM Vorton Projector fix already exposed once: because the check was duplicated, the fix for the Vorton Projector's blind spot had to be applied by hand in both places separately (and in weaponCategoryFromGroup(), a third, structurally different function) — fixing one copy and missing another would have left a Stormbringer's weapon invisible in exactly one of those code paths.

The fix

Extracted the duplicated regex into a single shared function, isWeaponLikeGroupName(groupName), declared once near weaponCategoryFromGroup(). Both classifyHighSlotItem() and getWeaponDamageInfo() now call this one function instead of maintaining their own copies. The next new weapon type EVE adds only needs this one function updated, not two (or three, counting weaponCategoryFromGroup(), which already had its own separate, correct handling and was left untouched).

Deliberately NOT touched: weaponCategoryFromGroup() itself remains a separate function with its own Bomb Launcher exclusion (if(g.includes('bomb')) return null;) — that is a DPS-correctness decision (bombs are a burst/alpha tool, not sustained DPS) distinct from the broader "does this look weapon-shaped" check the other two functions need. isWeaponLikeGroupName() intentionally still returns true for a Bomb Launcher's group name ("Missile Launcher Bomb" contains "launcher"), exactly matching the pre-refactor behavior — confirmed by direct test below.

Files changed

  • weaponCategoryFromGroup() — unchanged (already a single, correct function).
  • New function isWeaponLikeGroupName(groupName) added near weaponCategoryFromGroup(), with a comment explaining exactly what it is and is not a replacement for.
  • classifyHighSlotItem() — its own inline regex copy removed, now calls isWeaponLikeGroupName(group.name).
  • getWeaponDamageInfo() — its own inline regex copy removed, now calls isWeaponLikeGroupName(group.name).

Remaining duplication (deliberately out of scope here)

ammoCategoryFromGroup() is a separate, already-single function for classifying charges/ammo (not weapons) and was not touched. The MODULE_DAMAGE_GROUP_CATEGORY lookup table (Gyrostabilizer/Heat Sink/BCS/etc. → category) is a different concern (low-slot damage modules, not weapon detection) and was not touched.
