Shared killmail links

FeatureTests 2026-10-27 · v2026.10.14.78 → v2026.10.14.79.

The owner first asked about sharing a pilot analysis with the My Ship side included, then: "maybe we should look at sharing assessment of a zkill entry instead. that way we know what to compare to", and "for now let's start with it just carrying the killmail." From the mockup (killmail_share_mockup.html): "a. menu b. agreed c. yes d. fine for now".

What you see

  • Copy share link is the first item of a loss's ⋮ menu, above Export fit. It copies the link of the loss on screen and reads "Copied!" for a moment.
  • The link is the page's address plus #kill=<killmail ID>/<hash>. The hash is the one ESI asks for, so the page fetches the killmail straight from ESI: zKillboard being slow or down doesn't affect a shared link.
  • Opening a link shows the Pilot Analyzer on that one loss:
    • the pilot's name, and the hull with a shared killmail tag instead of the hull dropdown;
    • the date, time and system, view on zKillboard, and See <pilot>'s <hull> losses, which runs the normal analysis;
    • one tab with the usual cards, compared against the viewer's own My Ship;
    • no Last Kill line (it's about the pilot's latest kill, and it's the part that needs zKillboard);
    • the tool's default module states, the same as any loss.
  • A zKillboard kill link pasted into the pilot box (zkillboard.com/kill/123456789/) opens the same view. This one makes a single zKillboard call to get the hash, and the address bar then shows the share link.
  • A link typed into the address bar of an open page loads too.
  • New error codes: SHARE-01 (zKillboard has no such killmail) and SHARE-02 (a link cut short). A wrong hash shows ESI-05, as any killmail ESI refuses.

Inputs only: the shared loss is built and computed by the same code as every Pilot loss (buildLossFits, split out of runFitForShip). This is also the base for the browser extension on the backlog (right-click a kill on zkillboard.com → open it here).

Lesson for future models

LESSON #71: a mock that accepts anything can't check what the feature adds.

  • The page checks' ESI mock returned the killmail for any hash, and the zKillboard stubs used made-up hashes. A broken share link would have passed.
  • When a feature depends on part of an API's contract, make the mock enforce it (here: 422 for a wrong hash, as ESI does), check the failure on purpose, and run a mutant that gets it slightly wrong.
