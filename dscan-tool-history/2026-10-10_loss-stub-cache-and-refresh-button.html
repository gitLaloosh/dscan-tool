Pilot Analyzer loss-list caching + "Refresh losses" button

Date: 2026-10-10   Status: Delivered, verified via code audit + 28/28 regression PASS + byte-identical diff + real-Chromium network-call-counting check

Reported by the owner: "i've noticed that re-clicking a hull from the list of 'Most flown across their last 30 recorded losses' re-fetches the data for those zkill records. Does it make more sense for that data to persist on the page for faster reload and fewer queries?" — followed by "there could be refresh button if that helps" when asked whether to implement it.

Root cause

Individual killmail details were already cached forever in killmailCache (safe — a killmail's own contents never change once it exists). But the zKillboard loss-list query itself — fetchLossesStubs(charId, shipTypeId), hitting zkillboard.com/api/losses/characterID/<id>/shipTypeID/<id>/ — had no caching at all. Every click on a candidate hull button called runFitForShip(), which called that function fresh every time, even when re-clicking a hull already viewed this session.

The fix

Added lossStubCache, a plain in-memory Map keyed by charId|shipTypeId (mirroring killmailCache's own no-TTL, page-lifetime-only pattern — a pilot picking up a brand-new loss in the few seconds/minutes spent flipping between candidate hulls is a vanishingly rare edge case, and a page reload clears it anyway). fetchLossesStubs() now checks this cache before hitting zKillboard.

Since a cache with no invalidation path is a real risk if a pilot does die again mid-session, added an explicit escape hatch: a new "Refresh losses" button next to "Analyze Pilot." A new lastFitRun variable captures exactly the lookup currently on screen (either the speculate-and-rank flow, or one specific hull) at the three places a fit gets rendered — the initial runFitCheck() call and each candidate-button click — so the button can re-invoke that exact same lookup with forceRefresh=true, which bypasses (and then refreshes) just that one cache entry. Nothing else is touched: killmailCache and the Phase 3 ESI type/group cache stay as they were, since there's nothing stale in either to refresh.

Files/functions changed

  • New lossStubCache Map, declared alongside killmailCache.
  • fetchLossesStubs(charId, shipTypeId, forceRefresh) — now checks/populates the cache, bypassable per-call.
  • speculateShip() and runFitForShip() — both gained a forceRefresh parameter threaded straight to fetchLossesStubs().
  • New module-level lastFitRun variable, assigned in runFitCheck() (both branches) and in each candidate button's click handler in renderCandidates().
  • New "Refresh losses" button + click handler next to "Analyze Pilot," calling lastFitRun(true).
