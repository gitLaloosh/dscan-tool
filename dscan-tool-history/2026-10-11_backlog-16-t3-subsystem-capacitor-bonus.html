Backlog #16: T3 Strategic Cruiser subsystem capacitor-capacity bonus

2026-10-11 · dscan-tool.html · "T3 subsystem capacitor bonus unmodeled -- some T3 Strategic Cruiser subsystems carry an intrinsic capacitor capacity/recharge bonus not currently read" (backlog item's own framing)

What the real mechanism is (live-ESI-verified, not guessed)

This file already has two established "flat self-add" patterns for T3 subsystem bonuses: a fitted subsystem can carry the SAME attribute id as a ship stat it feeds (shield HP via attribute 263, hull HP via attribute 2688), consumed by an ItemModifier effect whose modified_attribute_id and modifying_attribute_id are identical. Capacitor capacity turns out to be a 3rd instance of exactly this pattern: effect 3811 (capacitorCapacityAddPassive) reads a subsystem's own attribute 482 (the same id as the ship's own CAPACITOR_CAPACITY_ATTR) and adds it directly to the ship's capacitor capacity, with no skill scaling involved (confirmed live: none of the 4 races' "Core Systems" skills carry any effect touching attribute 482 at all).

Found while building this fix's own regression coverage, not assumed: this self-add is NOT exclusive to the Core subsystem slot. Each race's "Reactor"-named Core variant (Legion 45623 Augmented Antimatter Reactor, Tengu 45626 Augmented Graviton Reactor, Proteus 45629 Augmented Fusion Reactor, Loki 45632 Augmented Nuclear Reactor, all +50 GJ, plus Legion's Energy Parasitic Complex 45624) carries it as expected -- but a real Legion fit already in the golden-fit set (legion_popejoy) revealed its OWN fitted Defensive subsystem (45586 Covert Reconfiguration, +200 GJ) and Offensive subsystem (45598 Liquid Crystal Magnifiers, +100 GJ) also carry this exact effect, independently confirmed live via ESI. So the real mechanism spans multiple subsystem slots, not just Core.

The fix

Rather than hand-build an exhaustive 48-subsystem (4 groups × 4 races × 3 variants) lookup table and risk missing an id -- the exact class of mistake the per-race EWAR/speed-agility subsystem tables elsewhere in this file were built to avoid -- this fix reuses the SAME generic "check unconditionally on every defensiveGroups item" approach already used for the Shield/Hull HP self-adds. A new SUBSYSTEM_CAPACITOR_CAPACITY_SELFADD_ATTR (482) is checked on every fitted item the same way; any item carrying a nonzero value for it contributes to a new flatCapacitorCapacityAdd, which folds into baseCapacitorCapacity before the Capacitor Management skill multiplier (same "flat adds first, then max-skill multiply" order already used for shield/armor/hull HP). This automatically picks up a capacitor bonus on any subsystem slot that carries one -- present or future -- with zero maintained id list, and correctly ignores ordinary capacitor-related modules (a Capacitor Battery's bonus lives on a different attribute id entirely, confirmed not to collide).

Verification

New golden fit loki_constructed_core_subsystem_capacitor_bonus: reuses the already-verified real Loki hull dogma from loki_zkb138935092 (base capacitorCapacity attribute 482=1300) + the Augmented Nuclear Reactor Core subsystem (45632) fitted, nothing else. Result: capacitorCapacity: 1688, exact match to hand-derived (1300+50)×1.25(CapMgmt@V)=1687.5.

Added capacitorCapacity expectations as NEGATIVE CONTROLS to 4 existing fits whose Core subsystem (where applicable) is NOT one of the capacitor-bonus variants: legion_popejoy (375 -- genuinely non-zero, from its real Defensive+Offensive subsystem contributions explained above, not a false positive), loki_zkb138935092 and loki_zkb138990669 (both 1875, Core subsystem is Immobility Drivers on both, unaffected), proteus_constructed_propulsion_speed_agility_asymmetry (1875, no Core subsystem fitted at all).

Reverting the fix in a throwaway copy of the file makes all 4 of those capacitorCapacity assertions correctly fail with the lower pre-fix baseline (e.g. legion_popejoy 375→0, loki_* 1875→1625, the new Loki fit 1688→1625), while every other assertion in the suite stays green -- confirms this coverage would actually catch the bug class regressing, AND incidentally proves the fix's broader (not Core-only) scope is real, not a quirk of the new fit alone.

Also added a capacitorCapacity flattening field to run_regression.mjs -- capacitor.capacity had no regression coverage at all before now.

Full suite: 68/68 fits, 324/324 assertions, ALL PASS.
