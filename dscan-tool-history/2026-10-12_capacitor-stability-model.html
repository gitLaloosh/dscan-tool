Capacitor stability model -- stable %, time-to-empty, Weaknesses flag

2026-10-12 · dscan-tool.html · feature backlog item #2: "we need to be able to accurately represent cap numbers for the fit, whether it's cap stable with modules activated or if it might be a weak spot that can be exploited"

What existed before this

The tool already computed peakRechargeRate, activeDrainPerSec, and netRate (= peak − drain), with a stable boolean (netRate >= 0) -- explicitly documented as a "simplified sustained approximation, not a full cap simulation." It never answered the two questions that actually matter for threat assessment: if stable, stable at what %? If not, drains dry in how long?

Grounding: pyfa's real source, not a guess

Cloned pyfa-org/Pyfa directly and read eos/saveddata/fit.py + eos/capSim.py. Two findings:

  1. This tool's existing peakRechargeRate = 2.5 × capacity / rechargeTime formula is already exactly right -- algebraically identical to pyfa's own recharge curve at its peak point (25% cap). No drift, nothing to fix there.
  2. Pyfa itself computes stability two different ways: a full event-driven simulator (capSim.py -- staggers multiple same-type modules, models cap-booster charges as reloadable "injectors") used for pyfa's own display, AND a much simpler closed-form shortcut pyfa's own code literally names cap_stable_eve ("the stability value as the EVE client computes it") -- solves for the stable % using just the average drain rate across active modules, no per-module timing. This second one is what the in-game capacitor readout itself shows (confirmed against [stated]'s own in-game screenshot: "Stable" badge + live Δ GJ/s).

Scope decision

Asked [stated] directly which to build, since it's a real fidelity/complexity tradeoff, not an accuracy one: port pyfa's full event simulator (exact match to pyfa in every case, substantially more code/new algorithmic subsystem) vs. the EVE-client closed form (matches the in-game readout exactly, much simpler, can diverge slightly from pyfa's own number when a fit has several of the same cap-cycling module). [stated] chose the EVE-client closed form.

The math

Recharge rate as a function of current cap: R(x) = (2×capacity/τ) × √x × (1−√x), x = currentCap/capacity, τ = rechargeTimeSec/5. Setting R(x) = avgDrain and solving (s = √x): s² − s + k = 0, k = avgDrain×τ/(2×capacity) -- real solution exists only when k ≤ 0.25, which is exactly the existing netRate ≥ 0 condition (nice confirmation the old boolean was already testing the right thing, just not reporting the number). Physically meaningful (self-correcting) root: s = (1+√(1−4k))/2, stablePct = s² × 100. Re-derived independently, then matched character-for-character against pyfa's own cap_stable_eve formula.

When unstable, no equilibrium exists -- time-to-empty is computed by RK4-integrating the same R(x) curve against the constant average drain, from a full capacitor down to zero.

Ran pyfa's own capSim.py (same clone) side by side with this tool's new JS implementation on matching synthetic inputs:

The stable-% closed form is an exact match to pyfa's own equivalent formula. Time-to-empty is a close approximation (~2%) for any normal multi-module fit, and a looser one (worst case measured: 18% long/optimistic) for a fit leaning on one slow, cap-hungry module relative to a small capacitor pool -- documented in-code rather than hidden, same standard as every other disclosed approximation in this file.

Implementation

  • New simulateCapacitorStability(capacity, rechargeTimeSec, avgDrainPerSec) + capRechargeRateAt() + formatDurationShort() (matches pyfa's own Xs/XmYs display convention).
  • estimate.capacitor gained stablePct, timeToEmptySec, timeToEmptyCapped (4h safety bound, for the rare near-exact-boundary case), weak, weakReason. stable is now the real simulation result rather than just the net-rate sign (the two always agree, by construction).
  • CAP_STABLE_WEAKNESS_PCT_THRESHOLD = 25 -- a judgment-call cutoff (not a CCP mechanic), same "tunable constant" status as TANK_TYPE_THRESHOLD. A fit stabilizing under this % is flagged weak: thin margin, any extra drain (a hostile neut, overheat, one more module cycling) can push it negative.
  • Capacitor card: new "Capacitor state" tile shows "Stable at X%" or "Drains dry in Xm Ys", colored red when weak.
  • Weaknesses card: when capacitor.weak, a new red "!" badge row appears directly below the weakest-damage-type badge (reuses the existing .ewar-badge.danger styling already used for the cyno-fit misc-trait flag) -- "Capacitor drains dry in 21s with every cap-using module cycling at once" or "Only cap stable at N% -- thin margin...".

Deliberately out of scope (flagged, not silently dropped)

  • Ship-level intrinsic capacitor capacity/recharge role bonuses (a SHIP_ROLE_BONUS-class gap, same shape as the resist/drone-damage sweeps already done elsewhere) -- not hull-audited this round. This affects the two INPUT numbers (capacity, peak recharge), not the stability math itself. Candidate for its own dedicated sweep later, same pattern as the 424-hull SHIP_RESIST_BONUS exhaustive sweep.
  • Ancillary Shield Booster/Armor Repairer drawing from a loaded Cap Booster charge instead of ship capacitor -- re-examined this session, NOT a bug: this tool's own existing HP-side convention already treats the "charge exhausted" state as the sustained baseline (same reasoning as the burst/sustained duality already modeled for Ancillary Armor Repairer HP output), so counting the module's base capacitorNeed as ship-cap drain is the internally-consistent choice, not an oversight.
  • Nosferatu/energy-vampire net cap gain -- depends on an opponent's own cap state, a two-ship interaction this tool doesn't model anywhere else. Deliberately excluded, same framing as drone engagement range (pilot-controlled, no honest single number).
