#9 -- TD Sharpshooter/Defense Mode: confirmed NOT a gap

No code change. The independent review flagged this as "may be display-only." Traced directly: TACTICAL_DESTROYER_MODE_BONUS's sharpshooter entry is folded into dmgSkillMult via tdSharpshooterMult in both the confirmed-ammo and cargo-fallback DPS branches, and its defense entry is folded into tdShieldResMult/tdArmorResMult/tdHullResMult right alongside the hull-intrinsic resist bonus in the effective-HP calc. Both the Pilot Analyzer and Fit Analyzer precompute all three modes up front and the UI toggle swaps which precomputed estimate is displayed. This has had dedicated regression coverage since 2026-10-08 -- confessor_zkb138993321_t3d_miscbonus (Sharpshooter default, dpsFixed 432→576) and confessor_zkb138993321_t3d_defense_mode (armor HP 3304→4953) -- so the independent reviewer's concern was stale/unfounded, not a real gap. No new fit added; the existing two already guard this.

#7 -- Smartbombs: REAL bug, fixed

classifyHighSlotItem() decided "is this a fixed-damage weapon" by checking for a nonzero RATE_OF_FIRE_ATTR (attribute 51). Live-ESI-confirmed 2026-10-11 (Small Proton Smartbomb I, type 1547, and Large Proton Smartbomb II, type 3979): a real smartbomb carries attribute 116 (explosive damage) and attribute 6 (capacitorNeed) but no attribute 51 at all -- its cycle time lives on attribute 73 (REP_CYCLE_DURATION_ATTR) instead, same as every other non-turret active module in this file. Pre-fix, every fitted smartbomb's cycleMs read 0, so it fell through to the 'ammo' branch instead of 'fixed-weapon' -- misclassified as a charge, which meant the per-flag weapon loop found no actual weapon item for that slot and silently dropped it. A fitted smartbomb's damage was never credited to dpsFixed, exactly as the backlog item suspected.
Caught on a real killmail, not just a constructed test. The existing golden fit rokh_zkb138993491_rolebonus_audit (a real 2026-10-08 loss with 8x Large Proton Smartbomb II fitted) had its dpsFixed expectation pinned at 123-135 with the comment "drones only" -- that comment was accidentally correct evidence of the exact bug being fixed now. Post-fix, that same real fit's dpsFixed is 369 (129 drone DPS + 240 from the 8 smartbombs, 30 DPS each: 300 damage / 10s cycle). Updated that fit's expected range to 363-375 with an UPDATE note explaining why.

Fix: cycleMs = attrVal(dogma, RATE_OF_FIRE_ATTR, 0) || attrVal(dogma, REP_CYCLE_DURATION_ATTR, 0) -- the same OR-fallback pattern the cap-drain code already used elsewhere in this file. Confirmed live that real ammo (Antimatter Charge S, Conflagration S, Scourge Rage Rocket) carries neither attribute, so this can't misclassify a genuine charge as a fixed-weapon.

#15 -- Cap drain RoF consistency: REAL bug, fixed

A self-consistency bug, not a live-ESI question: the capacitor-drain loop read each cap-using module's cycle time directly off its raw dogma attribute, with none of the RoF skill (Rapid Firing, assumed max-level everywhere else in this tool), hull SHIP_ROLE_BONUS 'rof' entry, or fitted-module RoF bonus that the DPS calc's own effectiveCycleSec applies to that exact same attribute. Net effect: a turret modeled as firing FASTER for DPS purposes was modeled as draining cap at its SLOWER, un-boosted rate -- understating capacitor drain for every weapon with a nonzero capacitorNeed (energy turrets, Precursor Entropic Disintegrators, EDENCOM Vorton Projectors; ordinary hybrid/projectile turrets and missile launchers carry capacitorNeed=0 and are unaffected).

Why it wasn't just a one-line fix: the early per-item loop that reads capacitorNeed runs before categoryMods (which holds the hull/module RoF multiplier) exists in the file's execution order -- it can't apply a bonus that hasn't been computed yet. Fix: added a second small pass, after categoryMods is built, that walks the same fitted-item list, finds turret/launcher items specifically (weaponCategoryFromGroup() !== null, which also correctly excludes smartbombs -- no RoF skill ever applies to one), backs out the naive raw-cycle-time contribution the early loop already added for that item, and re-adds it using the exact same effectiveCycleSec formula the DPS calc itself uses.
