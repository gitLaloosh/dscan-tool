Implants and boosters from an EFT paste (Phase 1)

FeaturePYFA CORETooling 2026-10-14 · v2026.10.14.11 → v2026.10.14.12 · Erik: "it does calculate their affect when passed as part of an EFT fit. let's implement it but in a way that it can be disabled for the pilot analyzer. if we ever decide to include pods, we can turn it on at that point."

What was checked first

  • pyfa applies them from an EFT paste, not from cargo. service/port/eft.py: a bare line naming an item with implantness (attr 331) or boosterness (attr 1087) becomes an implant or booster; Name x1 is cargo, and Fit.calculateModifiedAttributes never runs cargo. pyfa keeps the first item per slot (HandledImplantList / HandledBoosterList). Erik confirmed in pyfa.
  • Ship killmails never list implants. Real zKillboard data (built-in browser; the sandbox can't reach zKillboard or ESI): a shuttle loss at 08:07:44 had none, the same pilot's pod 9 s later listed 10, all at flag 89. Boosters appeared on none of ~1,000 pod losses. So the Pilot Analyzer has nothing to apply; Erik chose a switch, off.
  • Scope. Every implant and booster effect run through the recorder: ~350 pyfa handlers reaching nearly every stat. Delivered in phases (Erik was told before work began).

What changed

  • New PYFA CORE section implant-calc (18 sections locked): IMPLANT_EFFECTS (310 effects, 361 rows: 183 implant, 127 booster) and IMPLANT_ATTRS by the new tools/gen_implant_table.py. Each effect is recorded in its carrier's own context ('implant' / 'booster') because handlers branch on it (e.g. stackingPenalties = 'implant' not in context). Set bonuses (Genolution, Amulet, Crystal, Snake, Halo, Talon...) are pyfa's early filteredItemMultiply on the other implants, the carrier included; the generator asserts they are unpenalized multiplies that no other set bonus changes. Booster side effects are skipped: pyfa's default is off. pyfaImplantSetup() applies the set bonuses and hands the rows to the stat code.
  • Applied in Phase 1: shield / armor / hull HP, resists (into the resonance pools, before the RAH), capacitor capacity and recharge, shield recharge, speed / agility / mass and propulsion speed factor (pyfaShipSpeed), signature, targeting range, scan resolution, sensor strength (including the Talon set's flat add), EWAR module values (pyfaEwarSetup), and the module attributes moduleAttrMult serves: capacitor need, cycle time, shield / armor / hull repair amount.
  • Not yet (Phase 2): weapon damage, rate of fire, range, tracking, missiles, drones, fighters (DEVIATIONS.md). The Fit card says so under the implant list.
  • Parsing: parseEftFit() puts implant and booster lines into the tally's Implants / Boosters groups; a second item for an occupied slot is listed as "Not applied, slot already taken". Before, these lines showed up as "Not recognized".
  • Pilot Analyzer switch: PILOT_ANALYZER_APPLY_IMPLANTS = false. buildLossTally() skips flag 89; on, it would put those items in Implants and the engine would apply them the same way.
  • Fit card and EFT export: Implants and Boosters lists with the scope note; the EFT export writes them as pyfa does (implants then boosters, by slot, between drones and cargo). A paste → export → paste round trip gives the same tally.

Found on the way

  • Recorder silent gate: Effect2298 (Halcyon B boosters, high-grade Talon/Grail/Jackal/Spur) boosts scan strength only if sensorBoost in implant.item.attributes. The recorder's source item answered False, so no rows. compare_implants.py caught it (22.8 vs pyfa 24.6). Fixed in pyfa_effects.py (SrcAttrs); every other generator is unchanged ("up to date").
  • Oracle hang: Effect2589 tests attr in booster.itemModifiedAttributes; the oracle's attribute dict had no __contains__, so Python iterated it forever. Added __contains__ / __iter__ like pyfa's ModifiedAttributeDict.
  • Checks that rebuild the reference dropped the implants: compare_speed.py / compare_modes.py rebuilt the oracle fit without them and reported the Rorqual's align as 294.8 against the tool's 280.3 (= Erik's pyfa). Fixed in the checks.

Lesson for future models

  • LESSONS_LEARNED #31 (new): confirm on real data that an input exists before building around it (ship killmails have no implants), and size a mechanic by running the recorder over every carrier of it (~350 handlers, not "Moderate"). A feature shipped in phases says on the page which numbers include it.
  • #28 (extended): the carrier itself can gate a handler silently (in implant.item.attributes).
  • #27 (extended): a missing stand-in method can hang a check, not only skip a handler; and a check that rebuilds the reference must carry every input of the original.
