Export fit to clipboard (EFT) -- context menu on the subtabs row

2026-10-12 · dscan-tool.html · backlog item: "add a context menu right aligned to the same row that the most recent losses links are... as the first item in that context menu, add the ability to export the fit to clipboard"

What shipped

A small, right-aligned kebab (⋮) menu now sits on the same row as the Pilot Analyzer's "most recent losses" tab buttons. Its first (only) item, "Export fit to clipboard (EFT)", copies the currently-active tab's fit to the clipboard in EFT text format -- the same format the existing Fit Analyzer's paste box already reads (pyfa, the EVE client's own Ctrl+A/Ctrl+C fitting-window copy, zKillboard "View as EFT", etc. all speak it). Clicking it briefly shows "Copied!" before the menu auto-closes.

Grounding

The exact EFT format (header line, slot-rack order and blank-line conventions, drone/fighter and cargo sections) was confirmed against pyfa's own real exporter source (service/port/eft.py, exportEft(), fetched live 2026-10-12) rather than assumed -- header [Ship, Fit]; one blank line between the header and the modules block and between slot racks; two blank lines between the modules block, the drones/fighters block, and the cargo block; each empty section skipped outright.

Implementation

New fitToEftText(shipName, fitName, tally, idToName, highSlotByFlag) serializes a fit's existing tally/highSlotByFlag (the same shapes buildLossTally() and estimateHpAndDps() already use -- no new data model). High-slot lines pair a module with its loaded charge using classifyHighSlotItem(), the same per-flag classifier the DPS estimator's own weapon loop already relies on, rather than assuming array order within a flag's item list (not guaranteed). highSlotByFlag is now also retained on each Pilot-Analyzer fit object (it was computed by buildLossTally() already, just previously discarded after the DPS estimate ran).

The menu itself is a plain <details>/<summary>, matching this file's existing collapsible-panel convention -- not a custom JS dropdown with a document-level click-outside listener, since no such pattern exists anywhere else in this file and renderFitTabs() replaces its container's innerHTML wholesale on every Pilot Analyzer search, which would otherwise leak one orphaned listener per re-render.

Caught during self-testing, not guessed at: the first module/charge split (treat whichever item classifyHighSlotItem calls 'ammo' as the charge) silently dropped a Sisters Expanded Probe Launcher's loaded Scanner Probe from the export entirely -- a probe deals no damage, so it classifies as 'other', not 'ammo'. Fixed: whichever item in a flag's pair is a weapon device (variable-weapon/fixed-weapon) is the module; the other slot in the pair is its charge/payload regardless of what classifyHighSlotItem calls that payload's own kind. Also added a defensive fallback (should never fire against real killmail/EFT-paste data, both of which always populate highSlotByFlag for every High-slot tally item) so a High-slot item with no flag pairing at all is still emitted as a plain line rather than silently dropped.

Known, deliberate scope limits

No [Empty X slot] placeholders -- a loss/pasted fit only ever tells us what was fitted, never a hull's total slot count. No Low/Mid-slot charge pairing beyond High slots -- mirrors the existing parseEftFit() parser's own documented scope (a Mid-slot Cap Booster's loaded charge round-trips as two unpaired Mid-slot lines, same as every other part of this tool already treats it; see the open capacitor-stats-research backlog item). No implants/boosters section -- this tool has never tracked that killmail flag range at all. A loaded High-slot charge's magazine quantity (e.g. "3285" missiles loaded) is lost on export by design, matching EFT format itself -- a fit definition states what's loaded, not how many rounds are in the chamber at a snapshot in time.

Verification

Round-trip self-consistency check (serialize a real fit → re-parse via the tool's own existing parseEftFit() → diff the resulting tally against the original): ran clean on three fits spanning the interesting cases -- loki_zkb138935092 (real T3C loss: 5 missile launchers + loaded ammo, subsystems, cap drone-free utility highs including the probe-launcher pairing case above), curse_zkb139073592_ewar (real EWAR Recon loss: cap warfare highs with no charges, EWAR mids with scripts, rigs, drone bay, cargo), and rifter_constructed_cyno_fitted (the defensive-fallback case: a single High-slot module with no highSlotByFlag entry at all). run_regression.mjs gained a new derived field, eftExportText, computed the same way for every fit; curse_zkb139073592_ewar's expected block now pins the exact full serialized string (chosen because it's the richest real-killmail fit already in this file -- exercises every rack, plus drones and cargo), so a future regression in the serializer or in its shared module/charge-pairing logic with classifyHighSlotItem() is caught exactly, not approximately.

Full suite: 74/74 fits, ALL PASS.
