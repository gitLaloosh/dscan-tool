Backlog #13: D-Scan name-parsing robustness

2026-10-11 · dscan-tool.html · "parseDscan()'s tab/multi-space fallback parsing may have edge cases with unusual pilot/ship/system names (punctuation, non-Latin characters) not yet stress-tested -- needs a set of real adversarial D-scan pastes to validate against, not a live-ESI question" (backlog item's own framing)

Grounding the test, not guessing it

This backlog item explicitly isn't an ESI question -- there's no live API that tells you what a copy-pasted D-Scan window looks like. Neither this tool's own files nor the EVE University wiki documented the raw paste format (the wiki page only covers the Ctrl+A/Ctrl+C mechanic, not the resulting text). Rather than guess at adversarial test lines from memory, I found an authoritative primary source instead: evepraisal/evepaste (fetched via its Nothing4You/eveparser fork, tests/parsers/dscan.py) -- the reference D-scan parser used across the EVE 3rd-party tool ecosystem, whose own test fixtures are real sampled paste output. Those fixtures also settled a tension that came up mid-investigation: EVE University's page says the on-screen D-Scan list "does not show distance" -- true of the visible columns, but the fixtures confirm the pasted text is always three tab-separated fields, <name-or-placeholder>\t<type>\t<distance>, which matches what this tool has always assumed.

Two real misreads found, both fixed

1. Locale-formatted distances (space as the thousands separator) weren't recognized as distances at all. The old regex (/^[\d,]+(\.\d+)?\s*(m|km|au|ly)?$/i) only allowed a comma inside the number. A real fixture line -- test\tNoctis\t3 225 m -- showed the EVE client can format a distance with a space-grouped thousands separator (locale-dependent) instead of a comma. That token failed to match, so it fell through into candidates as a bogus ESI name-resolution target instead of being recognized as the distance.

This is distinct from the NBSP-normalization fix already in the file from independent review finding #20: that fix only swaps the character (U+00A0 → regular space) before splitting -- it doesn't touch whether the distance-matching regex can read a number with an interior space at all. Confirmed directly: even after that normalization, "3 225 m" (now a perfectly ordinary ASCII space) still failed to match the old regex. Fixed by widening it to tolerate interior spaces/NBSP as digit-group separators: /^\d[\d,\s ]*(\.\d+)?\s*(m|km|au|ly)?$/i.

2. A bare "-" distance (same-grid / no distance read) wasn't recognized either. One of the evepraisal fixtures is exactly this case: some dude's Stabber Fleet Issue\tStabber Fleet Issue\t-. "-" doesn't look like a number, so it leaked into candidates too, and the row's distance came back empty instead of carrying the "-" through. Fixed with a small dedicated check (/^-+$/) alongside the main distance regex.

Real-world severity of both: low. distance is only ever read in one place in the whole file -- the debug "Show parsed rows" panel (candidates: ... · distance: "...") -- so the only visible symptom before this fix was that panel showing an extra bogus candidate and a blank distance for these two cases. ESI itself already silently drops unresolvable candidates like "-" or "3 225 m" when resolving names, so neither leak ever reached actual ship/structure/pilot results. Still, both are real misreads of what parseDscan() is supposed to do, and cheap to fix correctly.

What was stress-tested and found to already be fine

The backlog item specifically flagged "unusual pilot/ship/system names (punctuation, non-Latin characters)" as untested. Ran all of the following through parseDscan() directly -- none exposed any bug, because JS's tab-split is character-set-agnostic and doesn't care about punctuation inside a field:

Also specifically checked the new, widened distance regex for false positives against real EVE null-sec system/structure names that start with a digit (a common naming pattern -- 6VDT-H, 4-07MU, 9HYS-T, 1DQ1-A, 4HWWF): none are mistaken for a distance, since they don't end in a unit or pure digit run.

Regression coverage added

parseDscan() had no dedicated regression coverage before this (it's architecturally separate from the killmail-based golden_fits.json/run_regression.mjs suite -- it's consumed only by the D-Scan tab, not estimateHpAndDps()). Added a new standalone script, dscan_parse_tests.mjs, covering the 4 evepraisal reference fixtures plus 14 constructed adversarial cases (18 total) with exact expected {candidates, distance} output for each. 18/18 PASS against the fixed code.

Also re-ran the full existing golden-fit suite to confirm this change (confined entirely to parseDscan(), untouched by any fit/DPS logic) didn't disturb anything else: 63/63 fits, 292/292 assertions, ALL PASS.
