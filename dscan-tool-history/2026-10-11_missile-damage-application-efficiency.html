Missile damage-application-efficiency (missile-side only)

2026-10-11 · dscan-tool.html · backlog item: damage-application-efficiency, scoped by explicit user direction to missile-side only this session ("1. ship missile-side only for now. 2. keep turret-side in the backlog. 3. the ability to determine which missiles (damage type, size, class...) should be used..."); output structured as reusable per-class data for a later counter-fit-generator feature ("we will use this for a later feature that will generate a fit to counter the one we're assessing as a threat")

Scope decision

Turret-side application efficiency needs the attacker's own tracking speed (not modeled anywhere in this tool, since D-Scan/killmail data never exposes it) and an assumed engagement range (no canonical source) -- both missing, so it stays explicitly deferred in the backlog rather than guessed. Missile-side application only needs the TARGET's own signature radius and speed (both already computed by this tool) plus each missile class's own explosion mechanics (public ESI data), so it's fully groundable now.

The formula (grounded, not guessed)

Sourced from eveuniversity.org's Missile_mechanics page (CC BY-SA 4.0), cross-checked against live ESI attribute names/values on 6 representative T1 named ammo types:

appliedFraction = min(1, S/E, ((S/E) x (Ve/Vt))^drf)

where S = target signature radius, Vt = target velocity, E = missile's Explosion Radius (ESI attribute 654), Ve = missile's Explosion Velocity (ESI attribute 653), drf = the missile's own aoeDamageReductionFactor (ESI attribute 1353).

Checked and explicitly excluded: aoeFalloff (ESI attribute 655, present on all missile ammo, value 1500 on every class fetched) is NOT part of this formula per eveuniversity's own sourced text -- disclosed as checked, not silently omitted.

drf is NOT a universal constant -- confirmed live it varies by class/tier: 0.604 (Light Missile) vs. 0.944 (Torpedo) vs. 0.882 (Cruise Missile/Heavy Assault Missile) vs. 0.682 (Heavy Missile) vs. 0.644 (Rocket). Must be read per-ammo, never hardcoded as one number.

Architecture: live fetch, not a hand-maintained table

Confirmed via live ESI fetch of 24 ammo types (6 classes x 4 damage types) that explosionVelocity/explosionRadius/drf/maxVelocity/flightTime are IDENTICAL across all 4 damage-type variants (Scourge/Inferno/Nova/Mjolnir) of the same class+tier -- only damage type+amount differs. This means ONE live fetch per class covers the application math for all 4 damage-type recommendations at that class.

Chosen specifically to avoid this project's own previously-identified ARCH-1 lesson (hand-maintained tables like SHIP_ROLE_BONUS/SHIP_RESIST_BONUS drift from live data and are the root cause of most historic bugs here): MISSILE_CLASS_REFERENCE_AMMO stores only 6 TYPE IDS (266 Rocket, 210 Light Missile, 209 Heavy Missile, 20307 Heavy Assault Missile, 203 Cruise Missile, 267 Torpedo). The actual explosionVelocity/explosionRadius/drf values are fetched live via the EXISTING getType()/IndexedDB-cached ESI pipeline at runtime, never hardcoded.

Deliberately excluded this pass (disclosed, not silently dropped): T2 ammo tiers (Precision/Fury/Javelin/Rage -- confirmed live they carry DIFFERENT drf/explosion values than their T1 base, a genuinely separate trade-off axis) and XL Torpedo/XL Cruise Missile (capital-only, scope control).

The fix

New missileAppliedFraction(sigRadius, targetVelocity, explosionVelocity, explosionRadius, drf) implements the formula exactly. rankMissileClasses(sigRadius, velocity) runs it against all 6 live-fetched reference-ammo profiles and sorts best-to-worst by applicationPct. Computed twice per fit using this file's existing dual-state convention (already used elsewhere for speed/alignTime/signatureRadius): once for cruising (base signature radius + cruising speed, no prop mod) and once for boosted (boosted signature radius + boosted speed, only when a prop mod is fitted) -- base/cruising and boosted numbers are never cross-mixed, since they're physically simultaneous states. The recommended damage TYPE (ammo name) reuses the already-existing weakest variable from the per-fit weighted-resist calculation -- not new logic, just paired with the new class ranking.

Result object gains a missileApplication: {ammoName, cruising: [...], boosted: [...] | null} field -- structured, reusable per-class data (per the user's own stated intent: "we will use this for a later feature that will generate a fit to counter the one we're assessing as a threat"), not just a rendered sentence. The Fit Analyzer's Weaknesses card Missile tile (missileRecTileHtml()) now shows the best-applying class+damage-type at cruising speed as the headline, flags low application (<50%) explicitly rather than silently recommending a missile that mostly won't land, and shows a 2nd line only when a prop mod is fitted AND its boosted state picks a genuinely different best class.

Deliberately left unchanged: the simpler plain D-Scan summary card's Missile line (RECS[weakest].missile) -- that code path has no signature-radius/speed data available (only raw hull dogma from a D-Scan, no fitting detail), so it correctly keeps using the old static damage-type-only text.

Verification

Regression-harness-only compatibility issue hit and fixed first: the new unconditional getType() calls for the 6 reference ammo ids broke every one of the (then-)70 existing golden fits with Type 266 fetch: not found, since the sandboxed fakeFetch only serves each fit's own pre-captured types blob. Fetched full live ESI /universe/types/{id}/ JSON for all 6 ids (203/209/210/266/267/20307) via the browser pane and injected them into every existing fit's types object (418 new entries across 70 fits; 2 fits already had one or more of these ids from their own missile loadout, left untouched). Confirmed this alone restores ALL PASS on every pre-existing assertion with no other regressions.

Constructed 2 new golden fits specifically isolating the new math:

  • rifter_constructed_missile_application_cruising_only: bare Rifter hull, NO weapons or modules fitted at all. Clean, hand-derivable inputs: sig radius 35 (hull attr552, no rigs), cruising speed 456.25 (hull attr37=365 x this file's MAX_NAVIGATION_MULT=1.25-at-V convention, no prop mod). Hand-computed ALL 6 class application percentages independently (Rocket 70.0% / Light Missile 50.8% / Heavy Missile 12.4% / HAM 8.6% / Cruise 2.6% / Torpedo 1.9%) and confirmed EVERY one matched the sandboxed output exactly -- not just the pinned top-ranked value.
  • crow_constructed_missile_application_dual_state: reuses the existing Crow+MWD Interceptor fit verbatim (already-verified signatureRadiusBase=35/Boosted=79) to isolate the cruising-vs-boosted pairing. Cruising: Rocket 63.0%. Boosted (sig 79, speed ~3790 after the MWD's ~7x speed multiplier and Interceptor-specific sig-bloom reduction): Rocket 30.2%. Hand-derivation off this fit's own rounded display values (79/3790) gave 30.3%, 0.1pp off the sandbox's 30.2% -- expected, per this project's established convention that rounding happens on unrounded internal intermediates, not already-rounded UI display values (same pattern documented for the Draugur/Kikimora range fixes).

run_regression.mjs changes: added a missileApplication flattening block (missileAmmoName, missileBestClassCruising/Pct, missileBestClassBoosted/Pct) following the file's existing per-feature flattening convention. Also fixed a latent bug this flattening exposed: closeEnough()'s tolerance comparison did raw numeric subtraction, which silently fails (NaN, always falsy) for the first-ever STRING-valued assertion field (missileBestClassCruising = "Rocket") -- added exact string-equality handling alongside the existing numeric-tolerance path.

Revert-sanity-check: neutralized missileAppliedFraction() to always return 1 in a throwaway copy. Every new *Pct assertion correctly FAILED (100 vs. the expected 70/63/30.2) -- confirms this coverage actually catches the math regressing. (The *ClassCruising/*ClassBoosted label assertions still happened to pass in that broken state, since a stable sort with every class tied at 100% leaves Rocket first by object-key insertion order -- a disclosed limitation of this particular revert method, not a gap in the Pct coverage, which is what actually exercises the formula.)

Full suite: 72/72 fits, ALL PASS.
