Weapon Range/Falloff fix — missile velocity/flight-time skills added (comprehensive skill audit, P1-D)

Context: fourth item in the phased sub-backlog from the comprehensive skill audit (P1-A/B/C delivered earlier today). This closes the missile half of Finding C, and with it the long-standing F1 gap that's been on the open-gaps list since the Weapon Range/Falloff feature first shipped 2026-10-10.

What was wrong

Missile max-travel-distance (velocity × flight time) assumed no skill training at all. Two real skills were entirely unmodeled:

  • Missile Projection (12442): own ESI description "10% bonus to all missiles' maximum velocity per level" → +50%@V.
  • Missile Bombardment (12441): "10% bonus to all missiles' maximum flight time per level" → +50%@V.

Both skills' effects are gated on the item requiring Missile Launcher Operation (type 3319) — confirmed live across 5 missile ammo families (Scourge Heavy Missile, Cruise Missile, Torpedo, Fury Light Missile, Rage Rocket) that this requirement is always present, but — same finding as the P1-C turret Gunnery check earlier today — not always in the same reqSkill slot (heavy/cruise/torpedo missiles carry it as reqSkill2/183; light missiles and rockets carry it as reqSkill3/184 instead). Unlike Sharpshooter/Trajectory Analysis (gated on the weapon), this pair is gated on the charge/ammo item itself — which is also where the velocity/flight-time attributes themselves already live, so the check reads the charge's own dogma, not the launcher's.

What changed in dscan-tool.html

  • New constants: MISSILE_LAUNCHER_OPERATION_SKILL_ID = 3319, MAX_MISSILE_PROJECTION_VELOCITY_MULT = 1.50, MAX_MISSILE_BOMBARDMENT_FLIGHT_TIME_MULT = 1.50.
  • In the missile range branch: missileSkillGated = REQUIRED_SKILL_ATTRS.some(attrId => attrVal(chargeDogma, attrId, 0) === MISSILE_LAUNCHER_OPERATION_SKILL_ID); when true (confirmed true for every missile checked, matching the skills' own "all missiles" description text), velocity and flight time are each multiplied by their respective skill constant before the travel-distance product.
  • Updated the in-app methodology disclosure to mention Missile Projection/Bombardment are assumed max-level.

Along the way, widened run_regression.mjs's rangeEstimates flattening from "first entry overall" to "first entry per kind" (turret vs. missile) — a fit with both a turret and a launcher fitted (e.g. the existing Hawk golden fit) would otherwise have silently hidden whichever kind's weapon wasn't enumerated first from ever being assertable.

Magnitude

Example (Rapid Light Missile Launcher II + Mjolnir Fury Light Missile, the real Caracal golden fit): 3750 m/s × 3.75s flight time = 14063m travel distance before this fix → 5625 m/s × 5.625s = 31641m after (×1.5 on each factor compounds to ×2.25 overall). A substantial increase in every missile fit's displayed range — this was a complete gap, not a partial undercount.

Verification

  • caracal_alyra (Rapid Light Missile Launcher II/Mjolnir Fury Light Missile): hand-derived 3750×1.5=5625 m/s, 3.75×1.5=5.625s, 5625×5.625=31640.625→31641m — sandbox produced 31641, exact match.
  • hawk_user (Rocket Launcher II/Mjolnir Rage Rocket, plus a 150mm Light AutoCannon II/Titanium Sabot S turret on the same fit): hand-derived 1875×1.5=2812.5 m/s, 2×1.5=3s, 2812.5×3=8437.5→8438m — sandbox produced 8438, exact match. This fit's mixed turret+missile loadout is what surfaced the run_regression.mjs flattening gap above; also picked up its turret's optimalM/falloffM (1350/5913) as a bonus P1-C assertion on a second, different weapon family (projectile) not previously covered.
  • Not pyfa-cross-checked — same bar as every other skill-audit fix today; grounded in each skill's own live ESI description text plus the reqSkill-slot verification across 5 missile families.

Regression suite

golden_fits.json unchanged in fit count (43), 2 fits (caracal_alyra, hawk_user) gained new expected range fields. run_regression.mjs's range flattening widened to per-kind. 43/43 PASS.
