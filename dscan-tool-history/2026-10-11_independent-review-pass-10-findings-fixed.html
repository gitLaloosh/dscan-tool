Independent review pass -- 10 findings fixed, grounded and regression-tested

Context: per Erik's earlier explicit request ("have a separate/different model do an independent review pass over dscan-tool.html"), a fresh opus-model subagent reviewed the file after the P2 UI polish delivery. Per the standing autonomous-backlog instruction ("when you're finished, just continue w/ any backlog items that you can without my input"), every finding below was independently re-verified against live ESI (never taken on the subagent's word alone, same grounding rule as every other change in this project) before any fix was implemented, and every fix got its own new, isolating golden-fit regression test. Full suite: 52/52 PASS (46 pre-existing + 6 new isolating fits added this pass).

1. Rig drawback attribute 1138 misrouted to signature radius for ALL rig families (finding #1)

Attribute 1138 is a generic magnitude container, not an inherently sig-radius-specific attribute -- different rig GROUPS route it to different target stats via their own group-specific effect: Rig Shield routes it to signature radius (effect 2716), Rig Armor routes the SAME raw attribute to agility instead (effect 2717), confirmed live on both. Before this fix, every rig's raw 1138 was pooled into signature radius unconditionally, so an armor rig's agility-drawback number was silently inflating sig radius while never touching agility at all. Fixed by gating each pool to its own rig group and adding a parallel agility-drawback pool for Rig Armor. New fit: Rifter + 1 armor rig + 1 shield rig, both carrying 1138=10, proving each routes to its correct, different stat. One real fit corrected (ishkor dual-prop-mod alignTime).

2. maxActiveDrones (attribute 352) read as a ship attribute (finding #2)

Attribute 352 is a CHARACTER attribute (from the Drones skill, "1 drone per level"), never present on any ship's own dogma -- a ship-dogma lookup with an Infinity fallback effectively disabled the active-drone cap entirely. Fixed to fall back to the assumed-max-level Drones skill cap (5) instead of Infinity. New fit: Vexor + 10x Hobgoblin II, proving only 5 are active even though bandwidth would allow 15. 3 real fits corrected (ishtar_alyra, rokh, curse -- all had overstated droneDps).

3. Sentry drone hull bonus dropped for hulls with a plain "drone" table entry (finding #3)

A hull's "Drones hitpoints and damage" bonus (confirmed via Dominix's own Type Bonus text, OwnerRequiredSkillModifier effect) makes no sentry/combat distinction at the dogma level for most drone-boat hulls -- but the lookup matched hull-bonus-table entries by exact category (bCat==='dronesentry'), so a plain 'drone' entry (Dominix, Armageddon, Vexor, etc.) never matched a fitted sentry drone, silently dropping the ENTIRE hull bonus. Hulls with a genuinely separate, intentionally different sentry number (Ishtar, Rattlesnake) still get that explicit number, unchanged. New fit: Dominix + 5x Garde II, confirming droneDps=408 (a clean 1.5x over the pre-fix 272, exactly matching the hull's +50% bonus now correctly applying).

4. Missile Specialization RoF bonus applied to every launcher, not just T2 (finding #4)

Same "required-skill-scales-a-container-attribute" pattern found elsewhere in this file: the Missile Specialization skill's RoF bonus only applies to launchers that specifically require it (T2 racial/size Specialization launchers), not T1/meta/faction launchers that only require the base Missile Launcher Operation skill. Fixed with the same generic reqSkill-membership check already used for turret Specialization. New fit: Rifter + Heavy Missile Launcher I (T1) + Scourge Heavy Missile, confirming dpsFixed=18 (no T2-only bonus leaking onto a T1 launcher).

5. Drone Avionics rig constant 5x too small (finding #6)

The code's own adjacent comment already correctly said "+25000 at V" -- only the constant itself was wrong (5000 instead of 25000), understating drone control range by 5x for any fit with this rig. One-line fix; 2 real fits corrected (ishtar_alyra, kronos_bastion -- droneControlRangeTotal).

6. Loaded charges (bombs/probes) polluting the defensive-module loop (finding #8)

A charge loaded into a High-slot weapon shares that weapon's exact tally flag (by design, so DPS can be computed from what's actually loaded) -- which means it also flows into the per-item defensive-module loop that reads several attributes UNCONDITIONALLY off every item in that set. Confirmed live this is harmless for ordinary ammo (missiles/turret charges carry none of those attributes), but an Electron Bomb genuinely carries its own signatureRadius=400 (its own stat as a deployed object) and a Warp Disrupt Probe carries its own =90 -- both were being added straight into the CARRYING ship's own signature radius. Fixed by excluding category_id 8 (Charge) items from this loop entirely. New fit: Rifter + Bomb Launcher I + Electron Bomb, confirming signatureRadiusBase=45 (base 35 + the launcher's own legitimate +10 flat add -- NOT +400 from the loaded bomb).

7. Signal Distortion Amplifier rig bonuses not stacking-penalized against each other (finding #14)

A prior in-code comment claimed (without actually checking the effect's modifier operator) that 2+ fitted copies "legitimately double the bonus." Re-checked live: the rig's own effects use operator 6 (PostPercent, LocationGroupModifier) -- the standard EVE modifier shape that DOES get the diminishing-returns stacking penalty against same-ship same-kind sources, consistent with the rig's own in-game "Penalty: using more than one..." description text. Fixed by pooling same-kind+same-field rig fractions and stacking-penalizing them together instead of applying each as an independent full-strength multiplicative stage. New fit: Rifter + Multispectral ECM II + 2x Signal Distortion Amplifier II, confirming jamStrength=3.886 (stacking-penalized), not the naive 3.9 two full-strength copies would give.

8. Failed killmail fetches cached forever (finding #17)

A transient fetch failure (network blip, momentary ESI rate-limit) was being cached into the same permanent, never-expiring Map used for successful killmail fetches -- meaning one failure for a given killmail would repeat forever for the rest of the page session, including through the "Refresh losses" button (which only ever bypassed a different cache, the loss-stub list, not this one). Fixed to only cache on success, so the very next attempt retries instead of replaying a stale failure. Pure code-logic fix, no dedicated regression coverage (not meaningfully unit-testable in this harness without simulating a two-call retry sequence).

9. Probe/bomb/interdiction-sphere launchers miscounted as "unmatched weapons" (finding #18)

These launchers are deliberately and correctly excluded from dpsFixed (not sustained DPS sources, matches their real in-game behavior) -- but the SEPARATE weapon-count bookkeeping that feeds the "N unaccounted for" UI message counted them anyway, since it incremented before checking whether the item was even a real DPS-category weapon. They could never resolve (their category is permanently null), so they were stuck inflating "unaccounted for" forever. Fixed by checking category first and skipping the whole accounting block for non-DPS launchers. Verified against a REAL fit already in the suite (the Loki killmail, which carries a Probe Launcher) -- previously-documented "KNOWN OPEN ITEM #2" is now resolved: variableWeaponCount 6->5, unmatchedWeaponCount 1->0.

10. Nits: dead no-op regex, 2 stale comments (finding #20)

D-scan paste parsing had a line replacing a regular space with itself (no-op) -- fixed to actually target non-breaking space (U+00A0), its apparent original intent. Two stale comments corrected: the Tactical Destroyer "propulsion: deliberately EMPTY" comment claimed zero effect on DPS/EHP, which went stale once Speed/Align time were built in a later phase (a later comment already half-corrected this but the original was never updated); and a capacitor-drain comment's list of "modules confirmed to never carry capacitorNeed" implicitly excluded Precursor/Vorton weapons, which weren't in scope when it was written and DO carry capacitorNeed (confirmed live) -- no code bug (the computation already reads the attribute generically), just misleading documentation.
