1. Reactivation delay (bug fix)

The bug. pyfa averages a module's cap use over its active cycle plus its reactivation delay (moduleReactivationDelay, attribute 669). The tool divided by the active cycle only.

pyfa source.

  • eos/saveddata/module.py getCycleParameters(): averageTime = activeTime + inactiveTime.
  • capUse divides cap need by that average time.
  • Fit.__generateDrain() feeds fullCycleTime = cycleTime + reactivationTime to the simulator.

2. pyfa's capacitor simulation (replaces the averaged model)

What it does. The stable % and time to empty now come from capSimPyfa(), a line-by-line port of pyfa's eos/capSim.py, run the way Fit.__runCapSim() runs it:

  • identical modules are staggered (turrets are not);
  • Capacitor Boosters inject only when the capacitor needs it, with clip and reload;
  • reload is off for everything else (pyfa's default);
  • the run lasts 6 hours, starting full.

The displayed value is pyfa's (lowest level + level before activations) / 2. When the capacitor goes negative, it shows the time of that activation instead.

Inputs. The engine builds a per-module drain list for each case it shows (best case, ASB out of charges, without boosts, confirmed charges, charge range). Each entry has cycle + reactivation delay, cap need after skills (weapons: after rate-of-fire skills and the loaded charge), turret yes/no, and the Capacitor Booster injectors. These lists are exposed as capacitor.simInputs. Identical lists are simulated once.

The old formula is kept on hover. pyfa calls it "EVE's stability value" (computed, never displayed). Hovering the ring shows it for anyone comparing with the in-game fitting window.

One deliberate difference from pyfa. pyfa's injector code takes max() of an empty list in one branch, which would crash. The port uses the evident intent: the injector that gives the most. This branch never ran in 1,683 comparisons.

Verification

  • pyfa's own simulator as the reference. tools/cap_sim_oracle.py imports pyfa's unmodified eos/capSim.py. Every comparison below had 0 mismatches:
    • regression_suite/compare_cap_sim.mjs runs every golden fit's three cases through both: 483 simulations, 109 of them unstable.
    • Two randomized batches of 600 drain lists each, with and without injectors and clips, mostly unstable and mostly stable.
    Values are compared after rounding pyfa's raw numbers the JavaScript way (Python's round() rounds halves to even).
  • Hand-built drain lists run through pyfa's simulator (tools/independent_checks/check_cap_sim.py, which reads nothing from index.html):
    • Curse: 54.0 s with its booster, 30.0 s without.
    • Hawk ASB: stable 95.9% charged, 9.0 s out of charges.
    Pinned, with notes.
  • Suites: 161/161 fits pass; v.27 fails 16 checks of the new set. Parse tests 280/280; node --check clean.
  • Speed: the full suite runs in 1.6 s. The heaviest single simulation (a stable fit with an injector, which can't use pyfa's repeat shortcut) takes about 50 ms.
  • Playwright, real page: capacitor card on Vexor, Hawk (ASB click) and the no-charge Vexor; Fit Analyzer, Pilot Analyzer, module states, drones and tactical modes. No console errors.

Lesson for future models

LESSONS #20 happened again, one day later. The v.26 fix followed the cycle time to rawCycleTime but stopped there. The next pyfa property, getCycleParameters(), adds the reactivation delay, and four hand derivations in the independent checks had the same gap (check_module_states.py: MJD, ADC; check_phase3.py: Suppressor, Nullifier), so they agreed with the bug. They were corrected afterwards, and the lesson was added to the checklist (steps 2 and 4) and to #3. Follow a value to where pyfa consumes it (capUse, Fit.__generateDrain), not just to where it is computed. When pyfa has a standalone piece like capSim.py, run it as the reference instead of re-deriving it by hand.
