Drone recommendation now driven by real calculated stats, not name buckets

2026-10-13 · index.html · follow-up to the Rorqual fix (same day, earlier doc)

The question that triggered this

After the Rorqual fix, Erik asked whether the "Industrial hull" label was an ESI/pyfa concept or something the tool invented, and whether the bug was "widespread." Then a sharper follow-up: "what data points would most accurately tell you which drones to use against it... accounting for every bit of work we do to determine speed, agility, sig radius, resistances, etc. do we determine weaknesses AFTER we run calculations for the fit or are we making assumptions based on potentially arbitrary names or classes we bundle them into?"

What was found

Mixed answer. Damage-TYPE selection (which race of drone) was already done right — computed from the real, post-module/post-skill resistance numbers on the Pilot/Fit Analyzer path (base-hull-only on the plain D-Scan path, which never sees modules at all — a data-availability limit, not a shortcut). Drone SIZE selection was exactly the arbitrary-name-bucket problem: sizeClassFromGroup() mapped the ESI group-name STRING straight to a size tier via the hand-written GROUP_TIER table, never touching the real calculated signature radius, speed, or agility the tool was already computing a few hundred lines later in the very same function for the Navigation & Targeting card.

Checking the rest of that old 'industrial' bucket against real class-average signature radii (EVE University's "rough guide" table, live-verified) confirmed the "widespread" suspicion: Freighters (≈10,515m) and Jump Freighters (≈9,840m) are both still in the exact same ballpark as Carriers (9,960m)/Dreadnoughts (11,200m) — i.e. the identical bug to the Rorqual, just not yet fixed. Mining Barges/Exhumers (≈200m) and Blockade Runners (105m, live-verified) are genuinely small, no bug there — but their 195-200m sig radius is actually bigger than a Cruiser's 120m, which already got medium drones under the old table, while Mining Barges/Exhumers themselves were still stuck on light. A smaller instance of the same root bug.

Redesign

Replaced the ESI-group-name-driven pick with one driven by this hull's own real signature radius (the dominant real factor in whether a drone's own tracking speed can land hits), with the ship's real cruising speed as a secondary override on the Pilot/Fit Analyzer path (speed determines whether a drone can even keep pace with a target over a sustained engagement, independent of whether it can track it at all).

Explicit design decision (Erik): "when calculating sig radius, never assume that MWD will be active for drone selection. assume that pilots are aware that activating their MWD will blow up their sig radius and they'll take a lot of damage. go with the smaller sig radius resulting from an inactive MWD." Implemented literally: the new logic is fed baseSignatureRadius (hull + flat module add-ons + rig drawbacks), never boostedSignatureRadius (which folds in the MWD's sig-bloom bonus) — both values the tool already computes, just previously unused for this purpose. The same "assume no prop mod active" reasoning was extended to the speed component (cruisingSpeed, not the boosted figure) for consistency, since an MWD inflates both numbers from the same activation — flagged as an extension of Erik's instruction rather than something he separately asked for, in case he'd rather treat an Afterburner (which doesn't bloom sig radius the way an MWD does) differently later.

New size-tier thresholds

A judgment call, not a verified game constant (flagged as such, same category as TANK_TYPE_THRESHOLD) — anchored against EVE University's own "rough guide" hull-class signature-radius table (wiki.eveuniversity.org/Signature_radius, live-verified), with breakpoints at the midpoint between adjacent real classes:

New sizeClassFromSignature(sigRadius, groupName) implements this, falling back to the old name-bucket sizeClassFromGroup() only when sigRadius is missing/zero (defensive, shouldn't happen for a real ship). GROUP_TIER/sizeClassFromGroup() stay in the file, demoted to fallback-only, since their historical fix comments (the Rorqual writeup) remain an accurate record.

Speed override (Pilot/Fit Analyzer only)

droneRecommendation() gained an optional third targetSpeed parameter. When provided (real, unboosted cruisingSpeed), it compares the sig-radius-picked drone's own real max velocity — live-verified via everef.net: Light ≈2,800 m/s (Hobgoblin I), Medium 2,016 m/s (Hammerhead II), Heavy 1,200 m/s (Ogre II), Sentry ≈0 m/s (stationary, confirmed via Bouncer II) — against the target's real speed, and steps toward a faster drone class if the target would outrun it. This generalizes the old hardcoded "sentry primary always gets a chase-alt" rule into a real speed comparison: a sentry's own speed is ~0, so it's still always overridden by any nonzero target speed (same observable behavior as before), but a genuinely fast heavy-tier target now also gets caught by the same check. The plain D-Scan path has no fit/skill context to compute a real cruising speed from, so targetSpeed is always undefined there and the function falls through to the original, simpler sentry-only caveat — unchanged behavior on that path aside from the sig-radius-driven tier pick itself.

Still flagged, not modeled: real drone tracking (hit chance) is a function of angular velocity at an assumed engagement range/transversal, which the tool has no honest source for from a kill or d-scan snapshot — same category of gap as the already-backlogged turret-side damage-application-efficiency item. Signature radius + speed is a strong, now real-data-driven heuristic, not a guarantee, and that caveat is worth surfacing in the UI at some point rather than only living in this doc.

Addendum (same day): Afterburner-aware speed

Erik, immediately after this fix: "as you said, ABs don't bloom sig radius so if using speeds with AB active is helpful (or would change which drone is recommended) to deal with the higher speeds, go ahead and make the change as you see fit."

The speed fed into droneRecommendation()'s targetSpeed parameter is now a new droneSpeedBasis value, computed right after the dual-prop-mod block (so both boostedSpeed and secondaryBoostedSpeed are available): if an Afterburner is fitted, use whichever of those two figures actually belongs to the AB (propModType/secondaryPropModType already tag which real module each one came from, from the existing 2026-10-11 dual-prop-mod fix); otherwise (MWD-only or no prop mod at all) fall back to the plain unboosted cruisingSpeed, exactly as before. An MWD's own boosted speed is still never used for this purpose, for the same sig-bloom reason as the base fix above — this only ever substitutes in the AB's number, never the MWD's, including on a dual-prop fit where the MWD happens to be the "primary" (higher speedFactor) prop mod.

Verification: isolated droneSpeedBasis's exact expression and ran it against 5 scenarios (no prop mod, AB only, MWD only, both with AB as the higher-speedFactor "primary", both with MWD as primary) — all 5 produced the intended value, including both dual-prop-mod cases correctly picking the AB's own boosted speed rather than the MWD's, regardless of which one the existing "primary" bookkeeping considers the winner. node --check clean. Regression suite re-run: 94/94 fits PASS, 280/280 parse tests PASS (pure refinement of an already-uncovered function family -- no existing fixture asserts on drone output).
