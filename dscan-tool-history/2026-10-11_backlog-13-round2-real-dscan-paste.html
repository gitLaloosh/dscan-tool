Backlog #13, round 2: a real D-scan paste beats a reference library

2026-10-11 · dscan-tool.html · follow-up to the earlier same-day #13 fix, after Erik supplied an actual D-Scan paste from his own client

Round 1 of this item (same day, earlier) verified parseDscan() against the evepraisal/evepaste reference parser's test fixtures -- a solid primary source, but a third-party one, for an older/generic client paste shape (3 tab-separated fields: name, type, distance). Erik then supplied a real paste from his own client, and it immediately exposed something the reference fixtures never showed at all.

What the real paste looks like

37604	Not Bane's	Apostle	64 km
672	.	Caldari Shuttle	-
606	Velator - Mids	Velator	129 km

Four tab-separated columns, not three -- a leading bare inventory-type-ID with no unit at all (confirmed: 606 is Velator's real ESI type_id, 644 is Typhoon's). This is additional information attached to the row that round 1's reference fixtures simply didn't have an example of.

Real bug, confirmed immediately on every single row of the real paste. The distance-matching regex's trailing unit suffix was OPTIONAL ((m|km|au|ly)?), so a bare integer with no unit -- exactly what the leading type-ID column is -- matched it too. Since the row-parsing loop takes the FIRST part that looks like a distance, the type-ID column was winning that race on every row, and the REAL, unit-bearing distance ("64 km") was getting shoved into candidates as noise instead.

Net effect on a real paste: distance was wrong (a type ID, not a distance) for every row. Ship-type detection itself mostly still worked by luck -- the real type name ("Apostle", "Velator") survived as one of the other candidates and still resolved fine via ESI -- but the distance field, the thing this whole function exists to extract alongside the name, was broken 100% of the time on real data.

Fix: made the unit suffix REQUIRED ((m|km|au|ly), no ?). Every real distance across both rounds of fixtures carries a unit, or is the bare "-" case (handled by its own separate check) -- never a bare number alone. A bare type ID now correctly falls through to candidates as harmless noise, the same way pilot names and other placeholders already do, instead of stealing the distance slot.

Verification

Ran Erik's full real paste (28 contacts) through the fixed function directly: every row's real distance is now correctly identified (with unit, or "-"), and every row's actual ship-type name survives into candidates. Spot-checked a sample against known ESI type IDs for sanity (Velator=606, Typhoon=644) rather than assuming.

Added all 28 rows as permanent regression coverage in dscan_parse_tests.mjs (5 new individual cases + a full-paste block check), plus re-ran the round-1 fixture suite and the full golden-fit suite to confirm nothing else moved. 51/51 PASS (dscan parse suite); 63/63 fits, 292/292 assertions, ALL PASS (golden-fit suite, untouched by this change but re-run for safety).

Lesson

A reputable third-party reference library's test fixtures are real primary-source data, but they're not necessarily complete primary-source data -- they reflect whatever client version/locale/UI state their author happened to sample. One real paste from Erik's own client surfaced a column shape that an entire established reference library's fixture set never once showed. Worth remembering for future "no live-ESI question, just needs real sample data" backlog items: a reference library is a strong starting point, not a substitute for the user's own real data when it's available.
