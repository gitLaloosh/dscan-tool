Addendum 3 (same day): header icons had a title attribute that practically never triggered

the owner: "icons in the column headers do not have hover text, they should." This looked wrong at first -- the "11/11 svg icons have a title attribute" check from the original implementation above was re-run and still passed, every icon really does carry title="". The gap was between has a title and can actually be hovered to see it: an SVG's default hover hit-test (pointer-events:visiblePainted) only responds over pixels that are actually painted -- fill or stroke. Most of these icons are stroke-only outlines (the Shield/Armor/Hull layer icons, Passive shield regen, Armor repair, Hull repair), so their real hoverable area was just their ~1.8px stroke line, not the visible icon shape. At 15-18px on screen, landing a mouse on a 1.8px line by accident is close to impossible -- functionally no hover text, even though the attribute was there the whole time.

Fix: every one of these icon-generating functions (resistanceLayerIconSvg(), repairsHeaderIconsHtml(), breakPointIconSvg()) now draws a fully transparent <rect width="24" height="24" fill="transparent"/> as the first (bottom-most) child, spanning the whole viewBox. A fill of transparent still counts as a real, specified paint for hit-testing purposes -- it's just invisible -- so the entire icon box becomes hoverable, not only whatever's drawn on top of it. Zero visual change (confirmed via screenshot).

Verified via headless render: sampled document.elementFromPoint() at the center and a near-corner point of all 11 icons in a populated card -- every single sample now resolves to the icon's own <svg> (or a child of it), where before this fix several of those same points would have missed the painted geometry entirely and hit the icon's container instead. Regression suite 94/94 + parse tests 280/280 still pass. index.html: 569,588 → 571,285 bytes.

Addendum 4 (same day): the hit-area fix wasn't the whole story -- the tooltip itself needed an SVG <title> child, not just the attribute

the owner, after Addendum 3 shipped: "the hover text still isn't showing up for me on the icons." Walked through the usual stale-cache suspects first (GitHub Pages vs local file, hard refresh) -- ruled out: he confirmed he's loading the local index.html directly. He then sent a DevTools screenshot of an inspected <svg class="c-shield" title="Passive shield regen" ...> -- the attribute WAS present, correctly valued, with the Addendum 3 hit-area rect right there too. So the file was current and structurally correct, and it still didn't work.

Root cause: a title HTML ATTRIBUTE on an <svg> root doesn't reliably trigger the browser's native hover tooltip the way it does on a plain HTML element -- Chrome (and most browsers) look for an actual SVG <title> CHILD ELEMENT instead, which is also the SVG-native way to give an element an accessible name (the same thing screen readers read). Every other title="" already in this file sits on a real HTML element -- .cap-gauge's div, .td-mode-btn's button, .fit-menu-btn's summary -- which is exactly why that house convention worked everywhere else and silently didn't here: this was the first place title="" landed directly on an <svg> root rather than an HTML wrapper around one.

Fix: all 11 icons (resistanceLayerIconSvg(), repairsHeaderIconsHtml(), breakPointIconSvg()) now also draw an SVG <title> element as their first child, holding the same text as the title="" attribute (kept, harmless, some tooling still reads it). The <title> child is what actually drives the tooltip; the attribute was never doing that job on its own.

Verified via headless render: confirmed a <title> element is present as firstElementChild on all 11 icons with matching text, and re-screenshotted the card -- zero visual change (the <title> element isn't rendered, same as the hidden hit-area rect). Regression suite 94/94 + parse tests 280/280 still pass. index.html: 571,285 → 572,891 bytes. the owner confirmed afterward: "that works!"
