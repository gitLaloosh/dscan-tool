Full module dogma-attribute audit — findings

2026-10-12 · findings only, no code changes made yet · prompted by the owner: "Would it be worth you doing a deep dive into all modules that exist in esi so we dont keep discovering things that are invisible to the tool?"

Method (grounded, not scoped by assumption)

Per the owner's explicit correction mid-investigation ("i wouldn't make any assumptions about accuracy candidates. see what is out there and then determine what the candidates are based on their attributes and how they're used"), this audit did NOT pre-filter by module category or by what the tool currently displays. A research pass enumerated every ESI/SDE "Module" category (category_id 7) group — 158 total, 151 with at least one currently-obtainable item — and pulled the FULL real dogma-attribute list for one representative item per group directly from pyfa's local cache of CCP's actual Static Data Export (everef.net/ESI/github/fuzzwork/hoboleaks were all network-blocked this session; the pyfa SDE cache is the same first-party CCP data those sites redistribute, and is what pyfa itself calculates against). 309 distinct attribute IDs were encountered; none were filtered as "irrelevant" at collection time. Several specific findings below (the Siege Module family, in particular) were then independently re-verified directly against the same SDE files in this session, not just taken from the research pass's report.

Every finding below is tied to (1) a real attribute, on a real item, with its real value, and (2) a direct read of index.html confirming whether that attribute is currently referenced anywhere. Nothing here is asserted from memory of EVE mechanics or recollection of the code.

Bucket 1 — Accuracy (affects a stat the tool already computes)

ACCURACY Dreadnought Siege Module gets no bonus at all — Bastion/Siege/Triage/Industrial Core are NOT one mechanism

The current code (SIEGE_ROF_BONUS_ATTR_A/B = attrs 3108/3109) treats all of group_id 515 ("Siege Module") as one generic RoF-doubling mechanism shared by Bastion Module (Marauders), Siege Module (Dreadnoughts), Triage Module (Carriers), and Industrial Core (Rorquals/capitals). Directly re-pulling every published item in group 515 from the SDE shows this is wrong:

Net effect: a Dreadnought in Siege Mode is the one real miss here — the tool's own comment ("A Bastion Module, Siege Module, Triage Module, or Industrial Core doubles turret/launcher rate of fire while active") is simply incorrect for 3 of these 4 module types, and for Siege Module specifically the tool isn't just missing a RoF change, it's missing a roughly 7-9x turret damage multiplier and 1.65-2.1x missile damage multiplier entirely — a dreadnought's sieged DPS is almost certainly reported far too low right now. No golden fit in the regression suite exercises the real Siege Module II item (type 4292) at all, which is why this was never caught.

ACCURACY Shield Boost Amplifier is entirely unhandled — the positive counterpart to the Power Relay penalty above

Shield Boost Amplifier II (group 338) carries attr 548 shieldBoostMultiplier = +36 — a real, common low-slot module for active-shield-tank ships that boosts the fitted Shield Booster's repair amount by 36%. Attribute 548 is not referenced anywhere in index.html. Both the penalty (Power Relay) and the bonus (Boost Amplifier) sides of this same attribute are missing, which means any active-shield-tank fit's "DPS required to break this tank" figure is currently wrong whenever either module is fitted.

ACCURACY Fitted Sensor Booster/Signal Amplifier/Remote Sensor Booster's own sensor-strength bonus isn't folded into the displayed sensor strength

The 2026-10-12 sensor-strength fix (MAX_SENSOR_COMPENSATION_MULT) correctly applies the universal Sensor Compensation skill (+20%@V), reading the ship's own base SCAN_STRENGTH_ATTRS (208-211). But a fitted Sensor Booster II / Signal Amplifier II / Remote Sensor Booster carries its own real scanGravimetricStrengthPercent/scanLadarStrengthPercent/scanMagnetometricStrengthPercent/scanRadarStrengthPercent bonus (attrs 1027-1030, e.g. +48% on Sensor Booster II) that boosts the SAME stat — and that module-level contribution is never read anywhere in the file. This directly affects "can I ECM this target" — a core use case given the tool's purpose.

Bucket 2 — Usefulness (real mechanic, zero current representation)

USEFULNESS Passive shield recharge has no equivalent to the capacitor-stability feature

Capacitor has a full stability card (capacity, recharge time, net rate, stable%). Shield has nothing equivalent, even though the exact same kind of real modules exist for it: Shield Recharger (group 39, attr134), Shield Flux Coil (group 770, attr134+146, a capacity/recharge tradeoff exactly like the Capacitor Flux Coil fixed today), Shield Power Relay, and Power Diagnostic System (both above). For a shield-buffer-vs-shield-regen-tanked ship, passive shield regen rate is as relevant to sustained-engagement threat assessment as capacitor stability already is.

USEFULNESS Command Burst modules (gang/warfare links) — zero representation

Group 1770 "Command Burst", e.g. Armor Command Burst II: real attrs include warfareBuff1ID/Value through warfareBuff4ID/Value, maxRange=15000, capacitorNeed=25, duration. A fitted Command Burst module identifies a fleet-support/boosting pilot rather than a pure damage/tackle threat — a real, useful threat-assessment signal this tool currently has no way to surface at all (confirmed: zero hits for "Command Burst" or "warfareBuff" anywhere in index.html).

USEFULNESS Interdiction Nullifier module — zero representation

Group 4117 (the actual fittable mid-slot module, e.g. Interdiction Nullifier II — distinct from the similarly-named T3 Strategic Cruiser propulsion subsystem already covered elsewhere in the file). Real effect: warp bubble immunity (attr 3120 warpBubbleImmuneBonus) plus a targeting-range penalty (attr 309 = −50%). Directly relevant to "how to effectively defeat them" — you cannot bubble this ship.

USEFULNESS Micro Jump Drive / Micro Jump Field Generator — zero representation

Groups 1189/1533: a large, real signature-radius spike while active (attr 973 signatureRadiusBonusPercent = +150%) plus an escape/repositioning teleport. Not referenced anywhere in the file. Relevant to predicting whether a target can disengage.

Bucket 3 — Not relevant (checked against real data or the tool's own already-documented scope, not assumed)

NEEDS THE OWNER Cloaking Device — real data contradicts what was said earlier in this conversation

The owner's earlier statement was that cloaking devices use capacitor, as a reason the module sweep shouldn't be pre-filtered by category. The real SDE data for the representative item (Improved Cloaking Device II, type 11577) carries NO capacitorNeed attribute (attr 6) at all — its full attribute list is hp/power/cpu/requiredSkill/maxVelocityModifier/cloakingTargetingDelay/scanResolutionMultiplier/techLevel/moduleReactivationDelay/stabilizeCloakDuration. This matches current EVE mechanics (cloaks had their capacitor cost removed in a past rebalance) as far as this data shows. Flagging rather than asserting: if a different cloak variant or an older mechanic was meant, happy to pull that specific typeID directly from the same local SDE cache.

NOT RELEVANT Drone Tracking Enhancer/Modules, turret optimalSigRadius (attr 620)

These only affect weapon-vs-target tracking/hit-chance. The tool's own documented methodology already states this is out of scope for every weapon type, deliberately: "this is how far it can reach, not how much of its damage lands on a given target at that range, which depends on the target's own signature radius and speed and isn't modeled." Consistent with an existing, disclosed design decision — not a gap.

NOT RELEVANT Remainder of the 241 unhandled attribute IDs

The bulk of what the sweep turned up and isn't listed above is: the module's own hp/power/cpu/techLevel/metaLevel/requiredSkillXLevel/canFitShipGroupXX/reloadTime/chargeRate/color-scheme/disallow-* flags (fitting metadata, not combat-relevant since the tool already assumes a valid, max-skill fit); every overload* attribute (heat/overheating isn't modeled anywhere in this file, consistently); jump drive/portal/cyno/clone vat bay/compression/entosis/scanning-for-exploration/mining-and-gas-harvesting attributes (industry/traversal mechanics, not ship-vs-ship combat); and capital-only doomsday/ECM-burst-projector/titan-phenomena attributes (true supercapital-only mechanics, far outside a d-scan threat assessment of normal fleets). None of these bear on assessing a ship/pilot's combat threat level.
