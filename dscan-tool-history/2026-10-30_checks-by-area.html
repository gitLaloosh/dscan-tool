Checks by area, and a ledger

ProcessChecks 2026-10-30 · page unchanged (v2026.10.30.2)

Why

The owner asked how often the delivery routine catches problems, then "yep, do it" to running only the checks a change needs. The evidence came from v2026.10.30.2, an Intel and UI change:

  • The pyfa chain took about 40 minutes. No calculation code had changed, so it could not have found anything.
  • The full page-check run took about 25 minutes. It caught nothing outside the changed area. Its failures were two intended expectation updates and three timing flakes that passed alone.
  • The real catches came from three places: the change's own new check and its mutants, the fast lints, and screenshots.

What changed

  • New tools/run_checks.py.
    • The fast lints always run, in about 30 seconds: personal data, UI rules, subtext, card names, request gates, error codes, the LESSONS index, and page-check areas.
    • Then a tier: area (the page checks tagged with the areas you name), calc (adds the pyfa chain and the calculation page checks) or all.
    • There are 8 areas: intel, system, pilot, fit, myship, calc, layout and extension.
    • Page checks run in parallel. A failure is run again on its own once. If it passes then, it is reported as flaky, not as a pass.
    • --check-tags fails when a page check has no area. It is a chain step, now 50 steps.
  • New tools/check_ledger.md.
    • Each delivery adds one row: version, tier, time, failed, flaky, and "Caught". "Caught" holds the real bugs a check stopped, filled in by hand.
    • Every 10 rows, the ledger is reviewed with the owner. A slow check that never catches anything moves to all only, and repeat flakes get fixed.
  • CLAUDE.md "Checks" says which tier to run when, and runs a full tier before a release, after a pyfa update, or every 5th delivery.
  • tools/README.md trimmed from 107 KB to 41 KB. Each row now says what the check does today and how to run it. The history stays in these dated docs. A duplicated intel_assess_check.py row was removed.
  • The runner's first area run caught something: intel_place_check.py printed a Python SyntaxWarning (an unescaped \s in a script string). The warning hid the result line, so it was fixed. The runner now reads the result from standard output, after any warnings.

Lesson for future models

None new. When a check's result is read from its last line, read it from standard output, not from standard output and standard error merged: a warning can land after the result.
