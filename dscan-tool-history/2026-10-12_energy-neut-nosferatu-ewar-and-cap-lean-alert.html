Part 1: Energy Neutralizer/Nosferatu as EWAR

Grounded live via ref-data.everef.net and fuzzwork (not assumed): Energy Neutralizer is ESI group 71, Energy Nosferatu is group 68. Neutralizer magnitude is attribute 97 (energyNeutralizerAmount, GJ/cycle, unconditional). Nosferatu magnitude is attribute 90 (powerTransferAmount, GJ/cycle, but only actually transfers while the target has more cap than the attacking ship -- a mechanic this card's effect text now states explicitly rather than implying a guaranteed drain). Neither module carries a skill-scaled magnitude bonus (checked via each type's own dogma_effects for a modifying skill effect -- none found), unlike most of the other EWAR kinds already on this card.

Both now register as a new 'drain' EWAR category with their own badge letter ("C", for cap warfare) and color. --cyan was the first instinct (thematically "energy") but failed the dataviz skill's validate_palette.js against the existing --tank-shield disrupt-badge color (ΔE 12.6, below the 15 normal-vision floor -- too close to tell apart even with full color vision). Iterated to #a66bd9 (violet), which passes every check as a 3-way categorical set with the existing tackle/disrupt badges on this tool's dark surface.

Part 1 data-completeness fix (found during verification)

Verifying the new fields against the one existing golden fit with a real fitted Nosferatu (ishkur_constructed_dual_prop_mod) surfaced two gaps in that fit's cached ESI stub, both predating this feature (the fit was built for dual-prop-mod/speed/sig testing, so its type snapshots only carried the attributes those tests needed):

  • The Nosferatu's own type stub (13001) was missing attribute 90 entirely → computed capPerCycle/capPerSec as 0. Added the live-confirmed value (10 GJ per 2.5s cycle = 4 GJ/s, ref-data.everef.net/types/13001).
  • The Ishkur hull's own type stub (12042) was missing attribute 55 (capacitor recharge time) entirely → this fit's existing capacitor-stability card (shipped earlier tonight) silently degraded to a meaningless "Stable at null%" display, caught via this fix's own Playwright screenshot. Added the live-confirmed value (187,500ms, ref-data.everef.net/types/12042) -- the card now correctly reads "Stable at 56.8%".

Both were missing fixture data, not code bugs -- but leaving them would have meant knowingly shipping a confusing/wrong-looking real-fit screenshot, so fixed as part of this same delivery rather than filed separately.

Part 2: cap-lean neut-vulnerability alert

Judgment call (made solo, [stated] asleep): yes, this is realistic to build honestly, because it needs zero new modeling. It's the exact same capWeak/stablePct/netRate signal the capacitor-stability model already computes and already surfaces on the Weaknesses card (shipped a few hours earlier tonight) -- this just re-surfaces it on the EWAR / Misc card with an offense-facing framing ("here's how to beat this fit") instead of the Weaknesses card's defense-facing one ("here's this fit's own flaw"), per the explicit request to put it there.

Deliberately did not try to predict whether a specific neut/nos would actually break the target's cap -- that depends on the attacker's own fit, a two-ship interaction this tool doesn't model anywhere else (same documented exclusion as "Nosferatu net cap gain" in the capacitor-stability history doc from earlier tonight). Instead it states the target's own margin number only: netRate GJ/s of extra average drain needed to flip the capacitor negative when stable-but-weak, or the existing time-to-empty when already unstable. That's honest and already-grounded, not a guess about the opponent's loadout.

Uses the same CAP_STABLE_WEAKNESS_PCT_THRESHOLD (25%) cutoff as the Weaknesses card flag, so the two stay consistent by construction -- a fit is never "weak" on one card and "fine" on the other.

Why a new badge color instead of reusing the red danger badge

The existing .ewar-badge.danger (red) already means "this fit threatens you" (currently used for the cyno-fitted flag). This new alert means the opposite -- "this fit is exploitable by you" -- so reusing red would misread as another threat warning. Tried green first (an intuitive "good news" color) but it failed validate_palette.js against the existing red danger badge (ΔE 4.9 deutan, below even the 6-8 floor -- classic red/green colorblind confusion, risky right next to an existing red badge in the same card). Settled on #4a8fd1 (blue), which passes every check against the full existing badge set on this dark surface.
