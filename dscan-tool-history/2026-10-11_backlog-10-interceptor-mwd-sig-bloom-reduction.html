Backlog #10: Interceptor MWD signature-radius-bloom reduction

2026-10-11 · dscan-tool.html · "Some hulls have an intrinsic bonus that HALVES (or otherwise reduces) the MWD sig-radius-bloom penalty — not currently modeled; needs live-ESI identification of which hulls carry this and the exact mechanism" (backlog item's own framing)

What the real mechanism is (live-ESI-verified, not guessed)

Fetched live dogma data for all 10 published hulls in ESI group 831 "Interceptor" (Crow, Crusader, Ares, Taranis, Raptor, Malediction, Stiletto, Claw, plus the 2 pirate-faction variants Whiptail and Imp). Every one of the 10 carries:

  • Attribute 568 eliteBonusInterceptor = -15 (uniform across all 10 hulls sampled).
  • Effect 3766 interceptorMWDSignatureRadiusBonus — domain shipID, LocationRequiredSkillModifier, modified_attribute_id: 554 (the same signatureRadiusBonus attribute a fitted MWD itself carries), modifying_attribute_id: 568, operator 6.

The Interceptors skill (type 12092) itself carries effect 703, which scales ship attribute 568 by the skill's own trained level -- so 568's static value as given by ESI (-15) is already the per-level magnitude, same convention this file uses elsewhere for X%/lvl hull bonuses. Cross-checked against EVE University's Crow page: "15% reduction in Microwarpdrive signature radius penalty" per Interceptors skill level -- matches exactly. At this file's standing assumed-max-skill convention (Interceptors@V), total reduction = -15 × 5 = -75%.

Critically, this reduction has to be applied to the module's own attribute 554, not pooled alongside the ship's other sig-radius percentage sources. Confirmed against pyfa's own eos/effects.py (Effect6730 moduleBonusMicrowarpdrive): the ship reads module.getModifiedItemAttr('signatureRadiusBonus') -- the fitted module's own 554 after any ship-side modifiers (like this one) have already reduced it -- and only then boosts the ship's own signatureRadius by that single number. So the fix multiplies the MWD's raw 554 value directly before it ever reaches the existing mwdSigRadiusBonusPct/stacking-pool code.

The bug this exposed

Interceptors showed the same MWD sig bloom as every other hull. With no group check at all, a Crow's boosted signature radius under a 5MN Y-T8 Compact Microwarpdrive (554 = +500%) computed as 35m base × 6.0 = 210m — identical to a Rifter fit with the exact same MWD. The real, correct figure (confirmed via live ESI and the game's own documented mechanic) is 35m × 2.25 = 79m, since the MWD's own 500% bonus gets cut to 125% (500 × 0.25) before it ever bloats the ship. That's roughly a 2.7x overstatement of how exposed an MWD-tanking Interceptor actually is while cycling its MWD -- directly relevant to this tool's whole "how hittable is this target" purpose, and specific to exactly the kind of fast tackle ship a d-scan analysis most needs to get right.

The fix

Added INTERCEPTOR_GROUP_ID (831), INTERCEPTOR_MWD_SIG_BONUS_ATTR (568), and MAX_INTERCEPTOR_SKILL_LEVEL (5, this file's standing max-skill convention). Where a fitted MWD's own attribute 554 is read (inside the existing propulsion-module loop), the ship's own group_id is checked against 831; if it matches, that MWD's 554 is multiplied by (1 + (568 × 5) / 100) = 0.25× before feeding into the pre-existing mwdSigRadiusBonusPct/applyStackingBonus() pipeline. A no-op (multiplies by 1) on every other hull -- confirmed directly: the same MWD on a Rifter still gives the unreduced 210m boosted figure.

Verification

Constructed a Crow + 5MN Y-T8 Compact MWD fit, all live-ESI dogma data, run through the tool's own sandboxed estimateHpAndDps(). Result: signatureRadius: {base:35, boosted:79}, matching the hand-derived math exactly. The identical MWD on a non-Interceptor hull (Rifter) gives boosted:210 -- unaffected, as expected. The pre-existing ishkur_constructed_dual_prop_mod fit (Assault Frigate, non-Interceptor, already has a real MWD fitted) was also re-run and its new signatureRadiusBase/signatureRadiusBoosted figures (39/234) pinned as a 2nd non-Interceptor control. Reverting the fix in a throwaway copy of the file makes the new Crow golden fit correctly fail (signatureRadiusBoosted: got 210, expected 79) while disturbing nothing else in the 66-fit suite -- confirms this coverage would actually catch the bug class regressing, not just look like it does.

Also added a signatureRadiusBoosted flattening field to run_regression.mjs -- the MWD-active figure had no regression coverage at all before now (only signatureRadiusBase was flattened, from the independent-review pass).

Full suite: 66/66 fits, 309/309 assertions, ALL PASS.
