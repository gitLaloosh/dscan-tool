Backlog #19: cargo-ammo-fallback fitting compatibility

2026-10-11 · dscan-tool.html · "the cargo-ammo-fallback DPS guess matches spare cargo ammo to an unresolved weapon by weapon CATEGORY ... but doesn't check the weapon's own specific chargeGroup compatibility ... may currently over-match ... needs verification of what compatibility data ESI exposes per-weapon" (backlog item's own framing)

What the real fitting mechanism is (live-ESI-verified, not guessed)

Fetched live dogma_attributes for a matched small/medium pair in every weapon family this tool models: 125mm Gatling AutoCannon I (small) / 220mm Vulcan AutoCannon I (medium) + EMP S/EMP M; Light/Heavy Entropic Disintegrator I + Occult S/M; Small/Medium Vorton Projector II + GalvaSurge Condenser Pack S/M; and separately every missile launcher size class (Rocket/Light/Heavy/Torpedo/Cruise Missile Launcher) with its own ammo. The real rule, confirmed identical across all of them:

  • A weapon declares up to 5 allowed charge group ids via attributes 604/605/606/609/610 (chargeGroup1-5). A charge is only loadable if its own group_id is one of those.
  • For turret-family weapons (projectile/hybrid/energy/precursor/vorton), that check alone is not enough: EVE packs every size of a given ammo family into ONE shared SDE group (group 83 "Projectile Ammo" holds EMP S and EMP M together; group 1987 holds both Entropic Disintegrator charge sizes; group 4062 holds both Vorton Condenser Pack sizes). The actual size gate is attribute 128 (chargeSize) -- present on BOTH the weapon (its required size) and the charge (its own size), using the same 1=small/2=medium/etc numbering on each side.
  • Missile launchers need no size attribute at all -- confirmed each size class (Rocket/Light/Heavy/Torpedo/Cruise) is its own dedicated SDE group with no attribute 128 on either side, so the group-id check alone fully disambiguates them.

Two real bugs this exposed

1. Turret-family size blindness (the case the backlog item named). The old code matched by broad category string (ammoCategoryFromGroup(a.group.name) === category) -- both EMP S and EMP M resolve to the same 'projectile' category, so a Small AutoCannon with spare Medium ammo in cargo would have been credited with that Medium ammo's (much higher) DPS. Replayed the old rule directly against the new golden fit: wrongly credits EMP M alone at 53 DPS for a single Small AutoCannon, vs. EMP S's correct 26 DPS -- roughly 2x overstated.
2. Missile launcher class collapse (worse, and not explicitly named by the backlog item, but the same root cause). The old category function collapsed all five missile launcher classes -- Rocket, Light Missile, Heavy Missile, Torpedo, Cruise Missile -- into one 'missile' bucket, despite each being its own mutually-exclusive weapon class in real EVE (a Rocket Launcher cannot load a Cruise Missile, full stop). Replayed the old rule: a spare Cruise Missile in cargo gets wrongly credited at 135 DPS for an empty Rocket Launcher, vs. the correct Mjolnir Rocket's 12 DPS -- over 11x overstated. This is a materially worse version of the exact failure mode the backlog item raised, just one level the item's own framing (turret size) didn't reach.

The fix

Added isChargeCompatibleWithWeapon(weaponDogma, chargeGroupId, chargeDogma): reads the weapon's chargeGroup1-5 attributes directly, requires the candidate's group_id to be among them, and additionally requires the chargeSize attribute to match when the weapon declares one (missile launchers don't, so that half is a no-op for them -- the group check alone already does the full job). This single, uniform rule replaces the old category-string match for cargo-ammo-fallback purposes, with no per-weapon-family special-casing needed.

ammoCategoryFromGroup() itself is now dead code (it had no other callers) and was removed, with its history preserved as a comment pointing to the new mechanism. weaponCategoryFromGroup() is untouched -- its broad category bucketing is still correct and still used for skill-bonus grouping (categoryMods), which is a genuinely different, coarser question than fitting compatibility.

Verification

Constructed two fits (Rifter + empty Small AutoCannon + cargo{EMP S, EMP M}; Rifter + empty Rocket Launcher + cargo{Mjolnir Rocket, Scourge Cruise Missile}), all live-ESI dogma data, run through the tool's own sandboxed buildLossTally()+estimateHpAndDps(). Both now correctly match only the compatible ammo (ammoEstimatesCount: 1 in each case) and exclude the incompatible one entirely -- confirmed via a negative control (cargo containing only the incompatible ammo produces an empty ammoEstimates, not a fallback match). Replaying the OLD rule against the same fits reproduces exactly the 53 DPS / 135 DPS over-credits above, and reverting the fix in a throwaway copy of the file makes both new regression fits fail with got 2, expected 1 (ammoEstimatesCount) while disturbing nothing else in the 65-fit suite -- confirms this coverage would actually catch the bug class regressing, not just look like it does.

Added both as permanent golden fits. Full suite: 65/65 fits, 304/304 assertions, ALL PASS.
