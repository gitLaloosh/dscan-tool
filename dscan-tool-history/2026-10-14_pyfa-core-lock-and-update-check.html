PYFA CORE lock, deviations list, pyfa update check

ProcessTooling 2026-10-14 · v2026.10.14.1 → v2026.10.14.2 (no calculation change)

The owner: "does the code have any mechanism for walling off code that is meant to directly replicate calculations being performed by pyfa that should NOT be changed directly for the purpose of being used by the tool differently?" He suggested: "1. wall off pyfa code from changes outside of pyfa version changes. 2. determine process for identifying and handling pyfa updates". Then: "yes".

What was there before

Nothing walled the pyfa code off. estimateHpAndDps() is one 3,300-line function in which pyfa formulas sit next to the tool's own choices. Generated tables had diff scripts, and the capacitor had pyfa's simulator as a reference, but the formulas were protected only by tests. Deliberate differences from pyfa were scattered through comments.

What changed

  • The rule (PYFA_CORE.md): the tool may change what goes into the pyfa calculation (module states, assumed charges, drones, the EWAR lockout) or how results are shown. It never changes how the calculation works.
  • 12 fenced sections in index.html (// ==== PYFA CORE BEGIN/END <id> ====):
    • ports: stacking penalty, capacitor simulation, Reactive Armor Hardener, module cycle time
    • generated tables: weapon range, module states
    • audited tables: signature, capacitor/repair, sensor, sensor strength, HP, cycle-time modifiers
  • The lock: tools/pyfa_core_manifest.json holds each section's SHA-256, what it mirrors in pyfa, and its verify commands. It also records the pyfa version it was verified against: v2.69.2, commit 3b9ce39, data 3579973, the same as the owner's pyfa. tools/check_pyfa_core.mjs checks it, and the regression suite runs it first, so a changed section fails the suite until it is re-verified and recorded with --update. Windows line endings don't count as a change.
  • DEVIATIONS.md: one list of every deliberate difference from pyfa, the inputs the tool chooses, what it shows beyond pyfa's fit stats, and known gaps. "A difference that isn't listed is a bug."
  • tools/pyfa_update_check.py, to run at the start of work. It compares the verified pyfa with the local checkout and with GitHub (latest release and master). --run runs the whole chain:
    • the core lock
    • golden-fit data vs SDE
    • both table generators
    • the effect-table audit
    • pyfa's capacitor simulator comparison
    • the regression suite
    Today: everything up to date and all 7 checks OK.
  • Instructions for future models:
    • CLAUDE.md now leads with the update check and the rule
    • the lessons checklist gained step 0 (update check; core or not?) and step 12 (verify and --update a changed section; list new deviations)
    • new LESSONS_LEARNED.md #23
  • Rides along: the reactivation-delay comment's "10-40x" corrected to "roughly 11-25x (2x for an Interceptor's Nullifier)".

Found while doing it

  • The general stacking helpers applyStacking / applyStackingBonus use a penalty table rounded to 3 decimals (0.869, 0.571, ...). pyfa uses the exact formula (0.86912, 0.57058, ...). They're used for resists, damage modules, shield-boost amplifiers, speed, mass and sensors, and the effect is a fraction of a percent. Listed in DEVIATIONS.md. They stay outside the core until each area is moved onto pyfaPenalizedProduct (already in the core) during the hand-table phases.
  • CCP's game data and pyfa's code change independently. The live page sees new ESI values at once, but tables built from pyfa or the SDE go stale; that is how the Akoman, Thunderchild and Hydra came to be missing. The update check covers both.

Lesson for future models

Before editing a calculation, find out whether it's inside a PYFA CORE section. If it is, the only valid reason to change it is to match pyfa, and the suite will tell you to re-verify. If you want the tool to behave differently from pyfa, change its inputs or its presentation, and add the difference to DEVIATIONS.md. See LESSONS_LEARNED.md #23.
