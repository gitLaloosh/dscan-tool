Capacitor Booster gain modeling, plus a boosted/unboosted dual display

2026-10-12 · dscan-tool.html · direct follow-up to the capacitor-stability model

The owner asked whether cap boosters (the module, or modules that use cap booster charges) were accounted for in the capacitor-stability numbers. They weren't -- the Capacitor Booster module was already correctly excluded from drain (it carries no capacitorNeed attribute), but its charge's cap injection was never modeled at all. The owner approved modeling it ("yes please"), then asked for an explicit UI indicator next to the stability figure, and finally asked to show both the boosted and unboosted values rather than burying the boosted number in a sentence.

Research, grounded live (ref-data.everef.net)

  • Capacitor Booster is ESI group 76. The module itself carries no capacitorNeed -- confirmed, consistent with this tool's existing comments.
  • The GJ injected per use (attribute 67, capacitorBonus) lives on the charge, not the module -- e.g. Navy Cap Booster 800 (type 32014) carries 800 GJ.
  • The module's own cycle time is attribute 73 (REP_CYCLE_DURATION_ATTR, already used elsewhere in this file for reppers) -- confirmed 12,750ms on a Medium F-RX Compact Capacitor Booster (type 4833).
  • Capacitor Systems Operation (the module's required skill) is the ship-recharge-time skill already modeled elsewhere -- not a magnitude-boosting skill for the booster itself (checked its dogma_effects directly; no modifier found).

Module↔charge pairing, for free

EVE's killmail data preserves per-flag module+charge pairing for any slot, not just High slots -- confirmed by inspecting the Curse fit's real killmail items: the Medium F-RX Compact Capacitor Booster and a single Navy Cap Booster 800 charge share Mid-slot flag 19, with 4 spare charges sitting unpaired in Cargo. The existing highSlotByFlag mechanism was generalized into a parallel midSlotByFlag (in both buildLossTally() and parseEftFit()), which meant this feature could reuse an existing real golden fit with zero new fixture data.

Design: a separate "boosted" figure, never netted into the baseline

Same convention already used for the Ancillary Armor Repairer's sustained-vs-burst split: a charge-based boost is a finite, unknown-quantity consumable (this tool has no way to know how many charges a pilot is carrying), so the conservative no-booster baseline stays the number that feeds the Weaknesses-card flag. The booster's gain is computed as its own separate stability simulation (capSimResultBoosted), surfaced alongside, never replacing, the baseline.

UI: both values shown, boosted clearly labeled

Per the owner's two follow-up requests, the Capacitor card's "Capacitor state" tile now shows:

  • The primary headline value: the conservative, no-booster baseline (unchanged position/styling from before -- still what the Weaknesses card reads).
  • A new, clearly separated sub-line carrying a BOOSTED badge (reusing the existing cyan .repairs-badge pill style already used for "ACTIVE REP" in the Resistance card) plus the boosted stability figure, the charge name, and its GJ/s gain -- e.g. "Drains dry in 1m20s with a loaded Navy Cap Booster 800 actively cycling (+62.7 GJ/s)".
  • When a Capacitor Booster is fitted but no loaded charge can be identified, an honest disclosure line instead of silently showing nothing or guessing a number.
