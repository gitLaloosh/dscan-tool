Capacitor ring: drain direction, status color, hover polish

PolishRequested by the owner 2026-10-13, same-day follow-up to the capacitor ring/boost-toggle build

Request

Three refinements to the new Capacitor-card ring:

  1. Have the ring visually drain in a clockwise manner (it didn't look right as originally built).
  2. Fix the boost toggle's hover state: with boost toggled ON, hovering the icon gave no visual feedback that it's a button, while toggled OFF the border color did change on hover.
  3. Use status colors instead of a single color: green→yellow→orange→red as the ring approaches 0%, with specific bucket boundaries (50-100%=green, 11-49%=yellow, >0%-<10%=orange, red when unstable). Mid-turn clarification: unstable should render as a full red ring, not an empty one.

Investigation and design

Direction. The original ring used the standard "progress ring" trick (stroke-dasharray=circumference, stroke-dashoffset=circumference×(1-fraction), SVG rotated -90° so the path start sits at 12 o'clock). Worked through the geometry and confirmed empirically with a side-by-side Playwright render before touching the real file: that formula makes the filled arc start at 12 and grow clockwise as the fraction rises — so as it drains (fraction falling), the fill's far edge recedes counterclockwise back toward 12. Not what "drains clockwise" should look like. Fixed by making the fill the trailing segment of the dash pattern instead (stroke-dasharray="fillLen gapLen", offset by -gapLen): now the gap (consumed/drained wedge) is what starts at 12 and grows clockwise as the fraction falls, with the remaining fill always ending back at 12 from the counterclockwise side — the boundary between filled and empty sweeps clockwise as the ring drains, same reading as a kitchen-timer pie. Verified both via a standalone geometry test (four fractions rendered side by side) and the real card in context (cropped/zoomed screenshot of the 35% state) before shipping.

Hover. Root cause: .cap-boost-toggle.active/.assumed-mode are both 2-class selectors — the same specificity as the plain :hover rule and later in source order, so they silently won outright regardless of hover state once toggled on. The only visible hover change on the OFF state was a generic button:hover rule elsewhere in the file (lower specificity, amber-tinted) bleeding through by coincidence on the properties the toggle's own :hover rule left untouched — never a deliberate design, and fully shadowed once .active/.assumed-mode's own higher-specificity background/border-color applied. Fixed with an explicit, equally deliberate hover rule per state (off/confident/assumed), each brightening its background and scaling up slightly (1.08×) on hover, with a short transition — none relying on the generic button fallback anymore.

Color. Added four new status-scale tokens (--cap-good/--cap-caution/--cap-warn/--cap-critical), picked from the dataviz skill's fixed status-palette family (good/warning/serious/critical) and contrast-checked against this ring's actual render surface — the --line-soft .estimate-stat background it sits on (#1a2126), not just a generic dark surface — all four clearing 3:1+ (5.59/7.99/5.27/3.88). --cap-critical reuses the existing --danger token directly rather than introducing a second red, consistent with how the rest of the file already uses it for "unstable/weak" everywhere else. The 10% boundary the owner's bucket list left undefined (yellow stated as 11-49%, orange as >0%-<10%) was resolved by treating ≥10% as caution/yellow, so the ranges meet with no gap. Per the mid-turn clarification, unstable is always is-critical regardless of its underlying stability %, and renders as a full ring (gapLen=0) rather than empty — matching the fuel-gauge-style convention of the stable states (full=healthy reads naturally as full=critical-and-draining too, just in red). The Weaknesses-card's own small cap-weak gauge (always shown only when unstable) got the same full-not-empty fix for consistency, since it's really the same underlying state as the Capacitor card's new critical ring.

Implementation

capRingHtml(): rewrote the dasharray/dashoffset math per the direction fix above, added a new capRingColorClass(result) helper implementing the bucket logic, and changed the unstable fraction from 0 to 1 (full ring). capWeakGaugeHtml(): changed its hardcoded dashoffset from circumference (always empty) to 0 (always full) — it's always-red already via its existing .cap-gauge-fill rule, no color-class change needed there. CSS: added the four new :root tokens with their contrast numbers documented inline; replaced the old single .cap-ring-fill.is-weak rule with four bucket classes; added explicit .cap-boost-toggle:hover/.active:hover/.assumed-mode:hover rules with a transition for smoothness.
